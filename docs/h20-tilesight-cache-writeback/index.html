Across the GPU
26,624 / 128 = 208 CTAs

Each thread block owns a 16 × 128 output tile. Its 128 threads form four warps.

Inside each CTA
2,752 / 64 = 43 K steps

Three buffered stages feed mma.sync through cp.async. Accumulators stay in registers.

B occupies 139.75 MiB, larger than this H20’s 60 MiB L2 cache. The compiled kernel uses 64 registers/thread and 55,296 bytes of dynamic shared memory. Its maximum occupancy is four CTAs per SM.

The arithmetic instructions did not change. All 848 GEMM machine-instruction/encoding lines match the archived kernel. TileSight’s parameters also remain unchanged, including our independently measured 3.860654536 TB/s HBM rate.

3. What is a dirty cache line?

A cache line is a block of data held in a cache. A clean line has no newer changes that must be preserved before replacement. A dirty line contains modified data that must eventually be written back to its backing memory.

Our original “flush” kernel reads and increments a separate 512 MiB buffer. It displaces GEMM inputs, but can leave modified lines in L2. When GEMM loads its inputs, replacing those lines can generate extra writes to HBM.

6. Check the hardware counters

Nsight Compute can measure L2 and HBM traffic, Tensor Core activity, arithmetic pipelines, and stalls. Nsight Systems provides the kernel durations used above.

The normal process was denied access by an administrator-only driver policy. A temporary profiling container with CAP_SYS_ADMIN successfully collected counters while preserving that host policy. The narrower CAP_PERFMON attempt was still denied on this installed stack.

Hardware counters now directly show additional HBM write traffic after write-based eviction. Three independent one-pass pairs measured 24.04–25.25 MB of additional HBM writes (22.93–24.08 MiB), while HBM reads stayed near 146.65 MB.

A separate complete metric comparison also found identical arithmetic instruction counts and identical SM-origin write requests to L2. Those 26,624 write sectors represent 851,968 bytes—the size of the output matrix. The extra HBM writes therefore do not come from the GEMM executing more output stores.

The complete comparison used three application-replay passes. The repeated HBM-only comparisons used one pass each. Compare traffic within each matched collection; do not pool different metric sets.

Counter collection perturbs execution. The 42.080 and 52.032 µs timings elsewhere on this page remain the earlier Nsight Systems measurements, not times obtained under Nsight Compute.

NVIDIA documents that DRAM byte counters include cache writebacks. These counters count traffic, not individual write addresses. Extra write traffic is measured directly; assigning every byte to a specific prior cache line remains an inference.

Combined with the wait, read-only replacement, and write-size controls, this provides strong evidence that dirty-cache eviction/writeback explains most of the timing gap. It does not yield an exact byte-by-byte explanation of every microsecond.

The Tensor activity percentage uses elapsed time in its denominator. Lower activity with unchanged Tensor instruction count is consistent with the same work taking longer; this percentage is not GEMM FLOPS utilization.

The equal Tensor instruction counts also match the intended matrix multiplication: 572,416 × 4,096 = 2,344,615,936 FLOPs = 2MNK. Each warp-level 16 × 8 × 16 multiply-accumulate represents 4,096 floating-point operations.

NVIDIA’s explanation of DRAM byte counters confirms that cache writebacks contribute to these counts. The counters support the writeback mechanism without identifying each line’s address.

Counter collection uses application replay with --cache-control none and --clock-control none, so the benchmark prepares its own cache state.

The preparation penalty is 10.880 µs for the original shape and 9.952 µs for the reduced shape. A similar absolute cost is a much larger fraction of a short kernel.

The old measurement was real. It measured GEMM after write-intensive preparation. That condition includes a memory state outside our TileSight plan. When comparing isolated cold-input GEMM, state the eviction method explicitly.

8. Keep the prediction fixed

We did not choose a new bandwidth to fit the improved result. The small-case prediction remains:

43 × (0.052438813 + 0.882718712) µs
+ 0.587479730 µs + 0.043717745 µs + 0.220679678 µs
= 41.0636507 µs

The first terms price repeated A and B loads. The remaining terms account for the MMA contribution left after overlap, then cast and store. This is a modeled overlapped schedule, not a sum of measured internal stages.

The model already treats all B loads as HBM misses and permits A reuse. It does not include dirty data left by a separate preparation kernel. Its separate 2 µs launch term is excluded from this comparison with device-only kernel duration.

The remaining 1.016 µs / 2.42% difference is unresolved. The experiment supports this workload and preparation; it does not establish universal TileSight accuracy. A production kernel that follows write-intensive work can still experience that extra traffic.
