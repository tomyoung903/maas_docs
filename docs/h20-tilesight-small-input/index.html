Each CTA owns a 16 × 128 output tile. All use the same rows of A and a different 128-column slice of B.

Inside one CTA

2,752 / 64 = 43 K steps

The CTA accumulates all 43 products into its one output tile. Its 128 threads form four warps.

Every tile is full: there are no padded output rows or columns. The chosen tile height is 16, matching M. Across the grid, each repeated operation occurs 208 × 43 = 8,944 times.

3. Describe one tile’s execution

The CUTLASS kernel uses cp.async to move inputs to shared memory and mma.sync Tensor Core instructions. The accumulator lives in registers. TileSight receives an explicit plan for that work.

Load B · 43 times64 × 128 FP16 values → shared memory
MMA · 43 timesUpdate the 16 × 128 FP32 accumulator
Cast C · onceConvert final values to FP16
Store C · onceWrite the 16 × 128 output to global memory

The compiled kernel allocates 64 registers/thread and 55,296 bytes of shared memory. Logical accumulator size is only part of register usage. The plan abstracts some address calculations, synchronization and internal data movement.

Show the plan-building code

The builder is given m = 16, n = 26,624, k = 2,752 and residency = 4. It records operations; it does not discover them from machine code.

kb=KernelBuilder('main',grid={'n':n//128,'m':m//16},threads=128,dispatch_order='linear_block_id',metadata={'kernel':'cutlass_mma_sync_cp_async','block_m':16,'block_n':128,'block_k':64})
A=kb.tensor('A',(m,k),'fp16'); B=kb.tensor('B',(k,n),'fp16'); C=kb.tensor('C',(m,n),'fp16')
As=kb.shared('A_s',(16,64),'fp16',stages=3);Bs=kb.shared('B_s',(64,128),'fp16',stages=3)
acc=kb.fragment('acc',(16,128),'fp32',carried=True);Cr=kb.fragment('C_r',(16,128),'fp16')
with kb.loop('k',k//64,stages=3) as loop:
    kb.copy(A['m','k'],As,name='load_A',engine='cp_async')
    kb.copy(B['k','n'],Bs,name='load_B',engine='cp_async')
    kb.gemm(As,Bs,acc,name='mma',compute_dtype='fp16',accumulation_dtype='fp32')
    with loop.epilogue():
        kb.cast(acc,Cr,name='cast_C',actor='epilogue')
        kb.copy(Cr,C['m','n'],name='store_C',engine='ldst')
program=kb.program(name='gemm_cp_async')
program=replace(program,launches=(replace(program.launches[0],residency=residency),))

4. Turn each operation into resource time

The device has 78 SMs. Its maximum occupancy is four of these CTAs per SM, giving 312 possible slots. Only 208 CTAs exist. The model packs them into 52 active SMs, at four CTAs each. Section 6 shows this assumption.

This changes the rate allocation: device-wide HBM and L2 rates are shared by 208 concurrent CTAs. Per-SM compute and shared-memory rates still use four resident CTAs per SM.

5. Use the saved overlap schedule

The solver selects an initiation interval (II) of 0.935157524 µs: the time between starting successive K steps. The raw resource lower bound is 0.883779672 µs. The selected schedule also has to satisfy ordering, dependencies, accumulator reuse and buffer limits.

Step 0: A starts at 0; B starts at 0.052438812 µs
MMA starts at 0.935157524 µs
Selected II ≈ load A + load B
= 0.052438813 + 0.882718712 = 0.935157524 µs

At that MMA start, the next step’s A load can begin. Most earlier MMA work therefore overlaps subsequent loads. This is the recorded solver’s schedule; using only the longest single-operation time would miss part of its interval.

Modeled operation timeline, not a measured internal GPU trace. Hover for exact times. The two views use different horizontal scales. Separate lanes do not imply one dedicated warp per lane.

6. Schedule 208 CTAs in one partial wave

Capacity = 78 SMs × 4 CTAs/SM = 312 slots
Concurrent work = min(208 CTAs, 312 slots) = 208 CTAs
Waves = ceiling(208 / 312) = 1
Tkernel body = 1 × 41.063650671 = 41.063650671 µs

Illustrative packing used by the model

208 occupied slots 104 unused slots

Under the model’s packing rule, active SMs = ceiling(208 / 4) = 52. The diagram illustrates 52 groups of four occupied slots, with 26 groups unused. It explains the rate allocation in section 4.

This is not a measured map of the physical SMs. CUDA decides actual CTA placement. Four is the measured maximum occupancy, while 52 active SMs is the model’s packing assumption. A real launch may distribute its CTAs differently.

The earlier larger grid had 624 CTAs and two full 312-slot waves. This grid has one partial wave. Do not multiply the small-case time by two, and do not assume that a partial wave leaves every resource at its full-wave per-CTA rate.

A wave is a scheduling summary; it does not insert a global synchronization barrier. TileSight separately reports a 2 µs launch term. It is excluded when comparing kernel-body prediction with device-only timing.

The primary measurement prepares the cache with a separate read-only sweep of 512 MiB, outside the timed interval. It replaces useful cached input copies with unrelated clean data. It does not make L2 literally empty.

The earlier write-based preparation produced an apparent 21.08% discrepancy. Subsequent controls and hardware counters showed extra HBM writes despite identical GEMM instructions. The prediction was not retuned. Read the cache-state investigation or watch the animation.
