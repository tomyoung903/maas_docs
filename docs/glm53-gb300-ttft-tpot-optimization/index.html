Counted by final behavior, there are six optimizations across scheduler_pp_mixin.py and prefill.py. The cumulative diff has 351 insertions and 74 deletions; line counts include guards and moved/indented code. Development preserved 12 source variants: ten performance candidates and two timing-instrumentation variants. This is not a count of commits or experiments.

The small page map identifies where KV pages live; this optimization does not copy the bulk KV cache into host memory. It preserves the page-map copy dependency and owns scratch/pinned buffers until completion, validates request/sender/row generation and cursors, and flushes or cancels before result handling, release, or a subsequent loop iteration. Alternate allocators, transports and unsupported modes retain the original path. Subsequent ATT25–27 work identified a separate bulk-KV producer dependency gap; the old page-map wait alone does not fence those bytes. ATT28 combines both producer-event paths with these six optimizations.

Definitions and corrected acceptance scope

Primary user latency: raw client TTFT runs from completed request-body upload to first meaningful generation event. Upload, connection setup, usage-only messages and DONE are excluded. Frontend and SGLang timers start and stop at different boundaries; coarse Grafana histogram percentiles must not be substituted for raw client percentiles.

Alex chart: trailing 20-second windows, grouped by protocol completion time, evaluated every second; sparse windows with fewer than three samples are null. Percentiles use linear interpolation. The follow-up independently rebuilt every saved chart point for all 15 uninstrumented runs, including the preceding baseline.

Earlier acceptance: 60-second windows grouped by request arrival, with latency followed to completion. ATT19 and ATT20 each passed 21,240 checked boundaries. This remains a valid narrow result, but does not imply the shorter chart windows pass.

TPOT=1,000 × (last generation time − first generation time) / (output tokens − 1)ms/token

The TPOT distribution is across successful requests with more than one output token. It is not the distribution of every individual inter-token gap. Multiple tokens can share one observed stream-event timestamp. About 46% of requests in these short-output trials have zero observed first-to-last span; that is coalescing at the client boundary, not infinite physical decode speed.

Cross-run changes below are observational, not randomized or counterbalanced causal estimates. Baseline failures also change the successful-request population. The historical 1P1D final runs match all 5,921 request identities and input/cache counts; the newer 2P1D arms use the separately verified 11,842-request candidate05.

TPOT stall evidence and regression question

The repeat has ten requests above 40 ms TPOT and four above 80 ms. Its whole-run p99 is 17.236 ms, but the worst 20-second p99 is 83.391 ms. A small cluster of stalled streams can therefore dominate a short-window p99 without changing the whole-run p99 much.

At approximately 350.937–352.463 elapsed seconds, four active streams share a 1.526-second gap in all observed token receipts. Sixteen new requests are dispatched during that gap. This argues against a complete freeze of the load-generator event loop. The exact trace joins below further localize the delay.

The stall pattern existed before the retained source patches: the depth-2 baseline already had three individual TPOT values above 80 ms; the depth-1 configuration-only trial had a 90.31 ms short-window p99. This disproves that the final map-copy patch first introduced the phenomenon. It does not establish that the patches have zero effect on its frequency or clustering.

Whole-run TPOT p99 improved from 21.39 ms in the original depth-2 baseline to 17.34 / 17.24 ms in the final runs. Exact joins recovered 37 traces / 1,998 spans. The ten TPOT-tail requests have Decode-forward durations of 0.189–0.334 seconds. Every enclosing Decode request ends 1.022–1.460 seconds after its Decode Scheduler span ends, measured within the same SGLang service. This avoids relying on client/server clock alignment for that gap. The evidence localizes much of the stall after Decode scheduling, in output handling/delivery; it does not yet identify the blocking function.

The TTFT-hot cohort instead has mean Prefill waiting of 2.091 seconds, versus 0.098 seconds in a nearby control cohort. At the worst TTFT chart point, TPOT p99 is only 16.56 ms. At the worst TPOT point, TTFT p50 is 2.995 seconds. The two spike mechanisms should be investigated separately. Both final runs have identical 20-second arrival-window uncached-load ranges of approximately 2.794–3.172M TPM, which weakens a large offered-load burst as the explanation.

A concrete KV handoff mismatch

ATT25 reproduced the third-request failure with a byte-level difference. Two retrieval answers were correct; the third cold request reached 256 tokens without a final answer. Its regular KV hashes differ between Prefill and Decode in global layers 58–77, exactly the last Prefill pipeline stage. No performance replay followed this finding.

The first two requests match all 156 logical pool tensors each. The failed request matches 136 of 156: all 78 DSA key/scale tensors match, while 20 regular KV tensors differ. The final 16 token rows match even in those 20 tensors; earlier Decode bytes contain substantially more zeros. Fifteen boundary snapshots join by exact internal request and bootstrap-room identity, covering about 3.0 GB of logical KV bytes. These observations suggest an early chunk read before its GPU writes complete, but do not yet establish the precise missing range or prove the cause.

Source inspection found a relevant existing dependency gap: with pipeline parallelism, this deployment disables the ordinary overlap scheduler. Its non-final chunk send can precede the prior forward-completion wait; the last pipeline rank lacks the proxy-send dependency present on the other ranks. ATT26 then added a broad producer-completion wait only to Prefill. All three answers were correct and all 468 compared pool tensors matched, while Decode and frontend remained unchanged. The expected zero hidden-state layout difference persisted. This supports the missing dependency as the cause of the observed KV mismatch; three requests with synchronous fingerprint diagnostics do not establish general correctness. ATT27 replaces the broad scheduler wait with a per-segment CUDA event consumed in Mooncake’s transfer thread, after outstanding-transfer accounting and before an abort/status recheck. Thirteen CPU fixtures execute the actual send, queue and worker methods. ATT27 also returned all three correct answers with all 468 pool tensor comparisons matching. Six prior Decode metadata files were hash-verified and excluded from this new trial. All queues drained. This change is not yet a validated performance result; the isolated Prefill151/Decode192 deployment subsequently passed all 15 predeclared retrieval requests with fingerprint capture disabled. This sequential correctness result is separate from sustained-load performance.

All observed metadata differences concern zero-filled hidden-state buffers with different layouts: 16 float32 values on Prefill versus 6,144 bfloat16 values on Decode. This difference appears on both passing and failing requests. The six other compared fields match. Zero speculative-seed validity remains a separate question; the layout difference alone is not evidence of random transport corruption.

ATT24 sent no probes. Before using its diagnostic, review found that the original DSA fingerprint helper included padding and omitted valid scale bytes on partial pages. A diagnostic-only correction passed twelve CPU fixtures, including a deliberately changed final scale byte that the original helper missed. An opt-in guard limits captures to the P/D boundary, preserving the existing EAGLE configuration without per-verify dumps. These are diagnostic changes, separate from the six retained performance changes.
