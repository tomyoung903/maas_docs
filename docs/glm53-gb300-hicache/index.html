先看结论

当前三层 HiCache 只属于五个 Prefill PP4 实例。它们各自拥有私有的 GPU L1 和 Host L2，并共同使用一个 2.344 TiB 的 Mooncake L3。Decode 的 16 张 GPU 另有 2.520 TiB request-local target L1，但没有启用 HiCache，也不会把 decode-generated continuation 自动写入 L2/L3。因此，全服务的 L1 是 4.843 TiB；真正接入 L2/L3 的 Prefill L1 是其中 2.323 TiB。

1 三层不是同一种介质

L1 消耗 GPU HBM；L2 和 L3 消耗不同节点上的 Host DRAM。不能把它们堆到同一条“集群内存利用率”上。

2 这是 inclusive cache

同一页可同时存在于 L1、L2 和 L3。三层物理 footprint 的和，不等于唯一 KV 数据量。

3 PP 只放大物理 bytes

PP0–PP3 保存相同 token positions 的不同 layer shards；逻辑 token 容量不能再乘以 4。

4 P→D 不是 L3 read

它使用 Mooncake TransferEngine 搬运一次请求的 KV，但绕过 MooncakeStore 对象生命周期。

不要把 10.672 TiB 写成“可缓存多少唯一 tokens”。其中 2.520 TiB 是 HiCache 之外的 Decode request pools；其余 8.152 TiB 是 inclusive Prefill HiCache，热页会在三层重复。一个 GLM-5.3 DSA logical page 还包含四个 PP stage 的主 KV 与 INDEXER objects；L3 有跨 replica 去重、不同 stage payload 大小、元数据和碎片，因此无法从 2.344 TiB 稳定反推固定 token capacity。
The hierarchy is about ownership

L1、L2、L3 分别意味着什么

L1private · fastest

Prefill + Decode GPU HBM

所有 engine 都有私有 device pages；只有 Prefill L1 接入 HiCache。Attention 只能直接消费 L1，因此 Prefill 的任何 L2/L3 hit 最终都必须回到这里。

  • Ownerone Prefill PP rank or Decode DP rank
  • ContentMLA KV + DSA INDEXER
  • Physical2.323 TiB Prefill + 2.520 TiB Decode
  • Logical9.252M / PP4 engine；3.136M / Decode DP rank
  • EvictionRadix-aware LRU，释放 device copy
L2private · persistent cache mode

Prefill local Host DRAM

与对应 rank 私有绑定的 pinned/CUDA Host NUMA pool。即使两个 Prefill 在同一物理主机，L2 也不是自动共享的。

  • Ownersame Prefill rank as its L1
  • Modehost-memory-mode=cache
  • Capacity13,878,208 logical slots / engine
  • Not disk/mnt/disk0/sglang-cache 不是 L2
L3shared · volatile

Mooncake object cache

所有五个 Prefill 共享的逻辑第三层。Master/etcd 管理 metadata 与 placement；KV payload 在 SGLang 和四个 Store segments 之间直传。

  • Ownercluster-wide Mooncake namespace
  • Capacity4 × 600 GiB = 2.344 TiB
  • StorageHost DRAM/EGM；无 SSD/NVMe offload
  • Failure作为 cache miss 回退重算，不影响正确性
GLM-5.3 DSA 完整性门槛：一个 page 的主 KV 命中不足以独立使用；对应 INDEXER object 也必须存在。SGLang 对 KV、INDEXER 以及全部 PP ranks 取连续命中前缀的最小值，确保所有 layer shards 对同一 token 边界达成一致。

Read / promotion · 最长连续可用 prefix当前显示读取与晋升路径
1Router 选 Prefill本地 KV events 为主，共享缓存只作为折扣后的路由信号。
2Radix 查 L1/L2返回一个连续 prefix：device pages 后面可接 host-only pages。
3检查 L3 suffix只查剩余的 64-token page-aligned suffix；阈值为 256 tokens。
4验证 DSA + PPKV 与 INDEXER 都存在；所有 ranks 对连续长度取最小值。
5L3 → L2 → L1wait_complete 在 admission 前等待已发起的 L3 操作结束。
6计算缺失 tail早期缺页会截断后续复用；partial final page 重新计算。

L3 不直接进入 GPU。Mooncake fetch 先写入新分配的 L2 pages，重新插入本地 Radix metadata，再执行 Host→Device load-back。

Write-through · 在淘汰之前建立下层副本当前显示写入路径
1产生完整 pagePrefill 新计算出一个或多个完整 64-token pages。
2L1 → L2write_through 异步执行 Device→Host；不是等到 eviction 才备份。
3D2H completion完成后发布 Host residency，并允许安排 storage backup。
4L2 → L3先查 object existence；缺失对象异步写入 Mooncake，已有对象去重。

每层都携带主 KV 与 DSA INDEXER sidecar；INDEXER 不是独立的“第四层”。

Eviction · 通常删除一份 inclusive copy当前显示回收路径
E1L1 回收已有 L2 backup 时只释放 HBM copy；Host/Storage copy 保留。
E2L2 回收释放本地 Host page 与 host-only metadata；L3 object 若存在仍保留。
E3L3 回收Mooncake 在 90% high watermark 附近按约 5% target 自主管理淘汰。
E4无连续副本缓存 miss 后 Prefill 重新计算；缓存从不作为 authoritative state。

当前五个 Prefill 的 host-pressure dropped tokens 为零；L3 已有成功 eviction history，且没有 SSD fallback。

P→D transfer · 同名技术，不同生命周期当前显示独立 Prefill-to-Decode 通道
1Prefill 完成本次请求所需 prompt KV 与 DSA state 已在 Prefill GPU。
2发布 transfer handle通过 Mooncake TransferEngine 建立 request-scoped 传输。
3直达 Decode GPU通道绕过 L3 object-cache box；L3 不是中转站。
4Decode 生成新生成 continuation 留在 Decode GPU，不自动 write-back 到 HiCache。

下一轮传回系统的是 token IDs。如果 continuation 尚未被 Prefill 缓存，Prefill 需要计算一次，之后才会由 write-through 进入 L1/L2/L3。

What deserves operational follow-up

两个不能被“Pod 都 Ready”掩盖的问题

HA service routing

Admin Service 也会命中 standby master

三个 master Pods 都通过 Kubernetes readiness，但只有 leader 的 service plane 提供 /get_all_segments。两个 standby 直接返回 503；Service selector 又包含三者，因此管理查询存在随机命中 standby 的风险。核心 SGLang data clients 通过 etcd 发现 leader，实际 L3 hit 已证明 payload path 正常。

Source-derived inference

Router 的 shared-cache credit 很可能查错 key schema

当前 legacy Dynamo 查询只检查 PP MLA KV key，不检查 DSA INDEXER；SGLang 则要求 KV + INDEXER 并自动给 Mooncake key 加 `zai-org/glm-5.3` prefix。部署参数没有显式匹配的 backend tag。这与 Router shared-cache credit 为零、而 engine 已有 76.06M L3 hit tokens 的现象一致。它影响路由优化，不否定 HiCache 实际读取。

Configuration and evidence chain

这张图来自哪些生产事实

Prefill HiCache

  • --enable-hierarchical-cache
  • --hicache-ratio 1.5
  • --hicache-io-backend direct
  • --hicache-mem-layout page_first_direct
  • --hicache-write-policy write_through
  • --hicache-storage-backend mooncake
  • --hicache-storage-prefetch-policy wait_complete

Deployment shape

  • Model: GLM-5.3 NVFP4；KV dtype: FP8 E4M3
  • Prefill: 5 replicas × PP4 = 20 GPUs
  • Decode: 2 groups × TP8 = 16 GPUs
  • Page size: 64 tokens；L3 prefetch threshold: 256 tokens
  • Mooncake: 4 × 600 GiB；offload disabled
  • MOONCAKE_LOCAL_BUFFER_SIZE=3221225472 是 3 GiB transfer workspace，不是 L3 capacity
