Mental Model

The MTP block is not a tiny language model driven by token IDs alone. For the row at position t, it combines the embedding of xt with the feature from position t-1, runs one separately trained sparse decoder layer, produces a draft feature for position t, and uses the target model's output head to predict xt+1.

The second input is the important new idea. The token says what symbol occupies this position; the preceding feature carries the target model's contextual summary of everything before it. The same token ID paired with a different preceding feature can therefore create a different fused state, attention KV, hidden output, and next-token distribution.

Terminology boundary. Immediately after target verification, the predecessor feature is the target model's final-RMSNorm output. During the inner recursive draft_forward steps, the target has not run on the new proposals yet, so the predecessor feature is the preceding draft output after the MTP layer's separate shared_head.norm. “Preceding hidden state” is the general rule; “preceding target hidden state” describes the reconditioning boundary.

This is why an already accepted token may still need another MTP pass. Its ID is unchanged, but replacing a recursively predicted predecessor feature with the target-produced predecessor feature changes the input to eh_proj and therefore changes the canonical draft state for that committed row.

The One-Position Offset

The cleanest indexing rule is: token at position t + feature from position t-1 → draft feature at t → logits for position t+1. The pair is deliberately offset; the MTP row does not pair a token with the target feature produced after that same token.

Why Accepted Tokens Run Again

1. draft_forward: provisional recurrence

selected feature for Bprev + token d1
↓
draft feature h̃D(d1) + token d2
↓
draft feature h̃D(d2) + token d3 …

Cheap and recursive: the target has not yet produced features for these proposed positions. The resulting draft KV is valid for proposing, but provisional.

2. Verify + draft_extend: target reconditioning

target verifies the tree and produces hT(Bprev), hT(d1), hT(d2), hT(d3)
↓
one batched NextN pass rebuilds d1, d2, d3, Bnew with those target-produced predecessor features
↓
select row 3's draft feature and logits to seed the next proposal chain

Target-conditioned does not mean the MTP output equals a target hidden state. It means the MTP row has been conditioned on the target-produced predecessor feature.

Why rerun d1-d3 if their token IDs already exist? Their original draft KV was computed from recursively predicted predecessor features. draft_extend supplies target-produced predecessor features, so it must recompute the accepted rows' MTP attention state. Bnew is the only novel token ID, but it is not the only row whose conditioning changes.

Hidden state and KV cache are related but not interchangeable. A hidden vector is the row-level feature entering or leaving the MTP block. The MTP decoder derives and stores its own attention KV from the fused input so future draft rows can attend to the committed draft prefix.

Checkpoint layer 78: NextN/MTP

enorm + hnorm + eh_proj + one DeepseekV2DecoderLayer(..., is_nextn=True) + its own shared-head norm.

Shared storage within each rank: target token embedding and target LM-head tensors. The MTP decoder weights themselves are separately stored and trained.

SGLang instantiates the draft decoder container with internal layer ID 0, then the weight loader maps checkpoint model.layers.78.* into model.decoder.*. That implementation remap does not turn it into target layer 0, and sharing the decoder family does not make it a copy of target layer 77.

Two unrelated “top-k” values appear in this system. EAGLE top-k=1 means one proposal branch per draft step. DSA TopK=2,048 means the attention indexer selects up to 2,048 KV positions. One controls proposal-tree width; the other controls sparse-attention positions.

In the pinned GLM-5.2 run, index_share_for_mtp_iteration = true. draft_extend computes fresh layer-78 DSA positions. The first recursive MTP forward also computes a fresh set; the next three forwards reuse it, and the worker clears the selection at the end of the round. This reuse applies to the selected integer positions, not to the indexer's cached keys, the draft MLA KV, or the hidden feature.

Misconceptions to Retire

“MTP is token-only.”

No. Every row fuses a token embedding with a predecessor feature before the decoder.

“One MTP forward emits five tokens.”

No. One row emits one next-token distribution. Recursive rows create the multi-token proposal chain.

“Only the bonus token needs draft_extend.”

No. Accepted draft rows need target-feature reconditioning even though their token IDs are unchanged.

“Target hidden history must be cached forever.”

No. The verify-time hidden block is temporary; target KV and target-conditioned draft KV are the persistent attention memories.

“Layer 78 copies layer 77.”

No. It is an appended, separately trained MTP block with its own fusion and decoder weights.

“Shared means one global tensor across all GPUs.”

No. The draft module aliases the target embedding/head storage within each rank's distributed placement.

“Five draft steps mean five MTP layers.”

No. GLM-5.2 has one extra NextN block. The runtime invokes that same block recurrently to build a deeper proposal chain.

Compact Glossary

target feature
A contextual hidden vector produced by the full 78-layer target.
draft feature
The one-layer MTP output recursively carried to the next proposal row.
draft KV
Attention memory written by the MTP decoder, distinct from both target KV and the row feature.
bonus token
The target-produced token after the accepted draft prefix; it is committed but was not an accepted draft.
draft_forward
The cheap recursive proposal phase using draft-produced features after its seed.
draft_extend
The reconciliation pass that consumes target-produced features and refreshes committed draft state.
