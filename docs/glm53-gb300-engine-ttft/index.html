2.1

Bootstrap admission

Bootstrap-queue entry → normal waiting-queue entry

This timer starts after the request has been put on the Prefill bootstrap path. It ends when Prefill admits the request to its normal waiting queue. It includes the coordination/admission delays between those two timestamps; it is not a direct network-handshake stopwatch.

With optimistic Prefill, a request can leave the bootstrap queue while the sender is still bootstrapping. Metadata-buffer availability and PP coordination can also affect admission. The histogram alone does not tell us which mechanism accounts for each observation.

2.2

Queueing and admission

Normal waiting-queue entry → first forward admission

This is the wall-clock interval before first forward admission. It includes scheduler waiting, any unfinished L3-prefetch readiness wait that blocks admission, and synchronous admission work such as preparing a cache load-back.

The scheduler may skip a request while storage prefetch is pending. It can also call init_load_back() before it records forward admission. Therefore “queue time” here is broader than time sitting untouched in a queue. It does not separately identify time attributable to GPU capacity, scheduling policy, cache setup, or remaining L3 work.

2.3

The full Prefill wall-clock span

First forward admission → final Prefill result-processing timestamp

For an ordinary unretracted Prefill attempt, the first-forward timestamp is set once. Intermediate chunks do not reset it. The ending observation is made when the final Prefill result is processed. Thus this spans all chunks of that attempt, not only the final chunk.

It can include GPU execution, pipeline/result-handling delays, inter-chunk scheduling gaps, and exposed host→GPU copy stalls. Async cache loading starts after the forward timestamp. It is not the sum of GPU kernel durations.

The separate chunked_prefill metric records intermediate chunk intervals and is nested inside this span. Its approximately 290.2 ms mean per intermediate observation must not be added to 639.1 ms.

2.4

Post-final-send completion tail

After the final KV-send call returns → sender completion, consensus, and cleanup

The timer starts after send_kv_chunk(..., last_chunk=True) returns. It ends after the success path has processed transfer completion, released cache state, and cleared sender resources.

In pipeline-parallel execution, completion IDs are coordinated across PP ranks before requests are cleaned up. This makes the rank-0 tail a completion/coordination/cleanup observation—not just rank 0’s NIC copy time.

Earlier chunks can already be transferring during the Prefill-forward span. Also, the final forward timestamp comes before output/cache bookkeeping and the final send call. That intervening gap is not covered by these four timers.

03 / Aggregation, not guesswork

How each mean and P99 was calculated

The metric families are histograms in seconds. For each pod’s matching series, compute a two-hour counter increase first; then sum across pods. The mean weights every histogram observation equally, so a busier pod contributes more than a quieter one.

μms=1,000 × (∑pods Δ duration sum) ÷ (∑pods Δ observation count)

Here Δ means the Prometheus increase(...[2h]) calculation. Its extrapolation can produce fractional counts; these are estimated observation counts, not fractional real requests. Applying the increase per series also handles counter resets before aggregation. Prometheus increase documentation.

P99 is calculated from the pooled cumulative bucket increments, retaining the le label. It is not an average of pod P99s, not the largest pod P99, and not an average of rolling chart P99s. Classic-histogram quantiles interpolate within the bucket containing the target rank. Prometheus histogram_quantile documentation.

q0.99=L + (U − L) × (0.99N − CL) ÷ (CU − CL)

L and U are the lower/upper bucket boundaries in seconds; CL and CU are their cumulative counts; N is the total observation-count increase. Counts use the same pooled window.

Precision is not accuracy. The API returns many decimals, but P99 is an estimate from finite-width buckets. For example, the queue P99 is interpolated inside a 5–10 s bucket. Report it as approximately 9.96 s, not as a nanosecond-accurate measurement.

Stage counts differ: bootstrap observes about 83,257 completions, queue about 83,326 admissions, forward about 83,328 completions, and transfer about 83,332 completions. Window boundaries, retries, and timer emission conditions can change those populations. These queries do not join individual request IDs.

04 / Different clocks, overlapping work

Why these four means do not sum to the Decode wait

The four Prefill means total 1,695.258 ms, versus 1,543.757 ms for Decode’s transfer wait. That is not an error to repair by subtracting a guessed “overlap” term:

  • Prefill’s bootstrap clock and Decode’s transfer-wait clock start at different milestones; Prefill work can already be underway when Decode starts waiting.
  • Sender completion/cleanup and receiver readiness/commit have different end boundaries.
  • There is a real instrumentation gap between the final Prefill result timestamp and the post-send transfer-start timestamp.
  • The means cover slightly different observation populations. Neither histogram contains request-ID pairing.
  • Optimistic retry/retraction paths can reset timing state. The simple full-chunk interpretation applies to an ordinary unretracted attempt.

Similarly, do not add 1.55 + 9.96 + 5.22 + 2.03 s to construct Engine P99. The slowest 1% of one stage need not be the slowest 1% of another. The large queue tail identifies an important area to inspect, but does not establish a unique causal bottleneck.

07 / Reproducibility

Re-run the four measurements

  1. Open the same Grafana deployment/window ↗ 261 and use the Prometheus datasource in Explore.
  2. Paste the mean or P99 query from Q1–Q4 (or download all eight queries). Use an instant query.
  3. The range selectors are pinned with @ 1788125400, so each query evaluates the two hours ending at 2026-08-30 21:30:00 UTC even if Explore’s current time changes.
  4. Expect mean results in milliseconds because the query multiplies by 1,000; P99 results remain in seconds.
  5. Compare against evidence.json: the saved API results include each sum, count, P99, all bucket increments, scope, evaluation timestamp, and PP-series count.

The frozen snapshot was fetched at 2026-09-06T04:52:33.573Z using authenticated POST /api/ds/query through the existing Chrome session. Each result returned HTTP/status 200 and the expected evaluation timestamp. This is a historical query, not “now minus two hours.” Future retention expiry may prevent a live replay; the saved evidence remains self-contained. No authentication material, request payloads, or browser-session state is included.
