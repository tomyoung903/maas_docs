Testing an L2-bound prediction

The original model predicted an L2 bottleneck. Follow-up tests found an instruction-family mismatch: this kernel’s HMMA path sustains less compute throughput than WGMMA. Read the evidence and corrected prediction.

1. Keep one concrete configuration

A64 × 2,048 × B2,048 × 9,984 = C64 × 9,984
FP16 inputs and output · FP32 accumulation · no scales, bias, or activation

This uses the same 16 × 128 × 64 CUTLASS tile as our narrow GEMM examples. The input matrices change; the tested kernel binary does not. The implementation uses cp.async, warp-level mma.sync, and register accumulators.

The CPU prediction was saved before GPU execution. It uses our H20 profile with 3.860654536 TB/s HBM, 8.123448629 TB/s L2, 139.22 TFLOP/s FP16 Tensor throughput, and 60 MiB L2 capacity. Only the HBM rate was independently calibrated on our host; the other rates remain the profile’s assumptions.

Measurement target: gpu-h20-5, physical GPU 4, NVIDIA H20, 78 SMs. GPUs 0–3 had other workloads. The selected GPU had no competing compute process during the recorded run. A cooperative lock was used; no exclusive machine reservation is claimed. No clock, power, driver, or host permission setting was changed.

The main result is the median of all 51 device-only kernel intervals, matched to the benchmark’s launch ledger. It excludes the 512 MiB read-only eviction sweep, allocations, input initialization, correctness checks, 100 warmups, and host launch overhead. The eviction sweep bypasses L1 and uses only 4 KiB of checksum writes; it avoids the previous write-based eviction artifact.

Both timing conditions use the same binary and deterministic inputs. All 638,976 output elements matched cuBLAS exactly for the multiples-of-1/8 fixture. That result does not promise bitwise equality for arbitrary floating-point inputs.

CUDA-event intervals and Nsight Compute replay durations are different timing definitions. They are retained as secondary evidence, not substituted for the Nsight Systems comparison. Warm means no explicit eviction between the priming and measured GEMM; it does not mean all input bytes hit in L2.

Warm preparation reduces the measured HBM reads by 52.85%, while the separate Nsight Systems median improves by only 0.544 µs. This supports substantial reuse and argues against HBM bandwidth alone explaining the runtime.

Does the hardware show L2 saturation?

A separate broader cold profile reports 36.44% for NVIDIA’s average LTS-throughput metric, 29.40% DRAM throughput, and 18.90% Tensor-pipeline active cycles. These are profiler-defined metrics, not the useful-byte and FLOP ratios at the end of this page. The profile’s replay duration is 36.352 µs; it is not the primary timing result.

L2 bandwidth saturation is not established by this experiment. The model is L2-bound, but the measured kernel is slower and the counters do not show the L2 throughput metric near its ceiling. Scheduling, issue constraints, synchronization, and memory-hierarchy details remain possible contributors; this run does not isolate them.

The broad profile counts 638,976 Tensor instructions. At 4,096 FLOPs per warp MMA instruction, that is exactly 2,617,245,696 FLOPs—the requested GEMM. It counts 128,696,096 L2-read bytes using sectors, whereas the model charges 184,025,088 declared input bytes to L2. These are different traffic descriptions. Their mismatch needs further investigation; it is not a reason to overwrite either result.

The broad profile required six application replays. Its measurements should not be merged with the smaller metric pair as though they were one execution. Counter access used a temporary, single-GPU container with the previously verified profiling capability; it was removed afterward and the host-wide profiling restriction was unchanged.

8. What the follow-up investigation established

The original plan used the wrong compute rate for its instruction family. The kernel uses mma.sync, which compiles to HMMA. Independent tests on our H20 sustain about 95.8 TFLOP/s on that path, compared with 142.6 TFLOP/s for Hopper WGMMA. TileSight assigned both paths the same generic 139.22 TFLOP/s. Correcting that assumption changes the modeled bottleneck from L2 to Tensor throughput. It reduces the error, but does not eliminate it.

The original 31.29% result above is retained. Its prediction and measurement were not replaced after seeing the answer. This follow-up ran on two H20 nodes; the final paired comparison used one idle GPU on the second node. No other workload was stopped and no paid GPU rental was needed.

Measure the instruction family independently

The HMMA microbenchmark performs a long stream of register-resident mma.sync.aligned.m16n8k16 operations. Each warp instruction does 4,096 FLOPs. It varies independent accumulator groups and warp supply, checks every output exactly, and compares two loop lengths. None of the GEMM timings enters this calibration.

All 72 valid HMMA configurations passed correctness. High-supply configurations form a stable 95–96 TFLOP/s plateau; the result is not one slow sample. Both probes reached the same 1,980 MHz SM and 2,619 MHz memory clocks during active execution. The stored H20 profile remains unchanged: the new rate is an explicit override for this HMMA analysis, not a global replacement that would slow WGMMA predictions.

Does microbenchmark mode guarantee correct constants?

No. H20().set_to_microbench() installs a table of constants. It does not detect or benchmark the current GPU. A useful calibration must identify the device, clocks, instruction family, access pattern, and what its byte or operation count includes.

The preset's 139.22 TFLOP/s closely matches a calculation at 1.743 GHz, while its 19.768 TB/s shared-memory rate matches 78 SMs × 1.980 GHz × 128 bytes/cycle. This numerical resemblance does not establish historical provenance. It does mean we should not assume one documented common clock or blindly rescale every value. Our independently measured instruction rates already correspond to the observed 1.980 GHz.

Changing its PTX load to ld.volatile.shared retains the loads; the compiled main loop then has 16 loads for 16 iterations, versus one load in the original unrolled loop. This does not prove that the defect generated the historical stored constant. The corrected probe also does not independently validate full-GPU mixed shared-memory reads and writes.

The lower register-load result is not a universal L2 ceiling. Both are effective loop throughputs, not isolated measurements of an internal hardware port.

Omitted operand traffic and instruction dependencies remain separate limitations.

Additional profile defects and traffic-accounting limits

The audit also found a no-op set_to_spec(), call-order-dependent register/INT32 values, and an inherited 24-block occupancy limit instead of the device's 32. Our fresh-object construction and explicit residency avoid these defects, so they are not explanations of this result.

The model counts 184,025,088 input-request bytes at L2. A verified cold counter pass counts 128,696,096 bytes from L2 read sectors, about 30% less. That counter includes all read sectors for the kernel, not separate A/B payloads. These different byte definitions limit direct bandwidth substitution. Lower physical traffic alone would reduce predicted service time, rather than explain the slower kernel.

Is our implementation contributing?

Yes. A second CUTLASS implementation computes the same FP16 matrices with Hopper TMA/WGMMA and a 64 × 128 × 64 tile. On the same GPU, it takes 24.576 µs instead of 34.239 µs for the original implementation, a 28.2% latency reduction. Both pass the same correctness and cache-preparation checks.

ImplementationCTA tile / countMatching predictionMeasured cold

The WGMMA change also reduces repeated operand requests and changes warp roles and output handling. It is not an isolated instruction replacement. Its model uses the new tile and one CTA per SM; hardware counters confirm exactly one CTA on each of the 78 SMs. Comparing its time with the old 23.616 µs plan would be invalid even though those two numbers look close.

What remains outside the simple model?

Nsight Compute attributes 1,097 of 1,115 sampled math-pipeline-throttle events to HMMA instructions. Shared-memory excessive wavefronts are zero in that profile. This locates execution pressure and weakens the bank-conflict hypothesis; stall samples cannot be added up as microseconds.

The five-operation plan does not explicitly time the kernel’s shared-to-register fragment loads, address instructions, waits, barriers, or unequal progress of resident CTAs. The compiled loop contains those operations. Diagnostic timestamps show four CTAs on each SM starting close together but finishing at different times. They are thread-0 observations from an instrumented build, not an exact timeline of every warp.

A separate long-running operand-loading probe sustains 94.68 TFLOP/s while interleaving the same three matrix loads per four HMMA instructions. The compiled loop was checked to retain those loads. Thus shared-to-register reads alone do not reproduce the residual slowdown: global copies, barriers, finite pipeline effects and scheduling still need separate attribution. The probe omits those mechanisms and is not a replacement generic compute rate.

The HMMA residual grows with K, so a fixed launch term cannot close it. In the WGMMA control, K = 512, 1,024, 2,048 and 4,096 leave roughly 4.75–5.27 µs above the original-rate model. Why we did not claim a numerically closer detailed plan was validated

An exploratory plan adds fragment operations and compiled instruction ordering. With the measured HMMA rate it predicts 32.595 µs. However, it groups four independently scheduled warps into one actor, conservatively delays register reuse, and does not exhaust its schedule search. Its numerical proximity is not enough to call it correct. Earlier source-text ordering also disagreed with compiled SASS; that result was withdrawn. All these experiments are retained separately from the accepted rate correction.

Conclusion: there is no evidence of incorrect GEMM arithmetic or an accidental timing inclusion. Implementation choice matters, and the model supplied too much compute capacity to this instruction family. The remaining gap is consistent with missing execution details; their separate costs remain unresolved. We have a defensible partial reconciliation, not a validated sub-5% prediction for this workload.

FLOP utilization (%) = work ÷ measured time ÷ (148 × 1012) × 100

The byte count reads each FP16 A and B element once and writes each FP16 C element once. It excludes repeated HBM fetches, cache writebacks, and other traffic. Therefore this is a useful-byte bandwidth ratio, not a hardware-counter measurement of total HBM utilization. A low ratio can coexist with additional HBM traffic or substantial L2 reuse.
