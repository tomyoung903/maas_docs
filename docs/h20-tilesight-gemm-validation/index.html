1. Start with an explicit configuration

C = AB,   M = N = K = 4,096
FP16 inputs and output · FP32 accumulation

There are no quantization scales, bias, or activation functions. This H20 path accumulates in ordinary registers, not Blackwell Tensor Memory.

We supplied a 128 × 128 output tile, a 64-element K step, and three pipeline stages. TileSight did not search for those dimensions. The actual CUTLASS kernel uses the same choices.

Show the Python call used to describe this GEMM
arch = H20().set_to_microbench()
program = gemm_program(
    m=4096, n=4096, k=4096,
    block_m=128, block_n=128, block_k=64,
    stages=3, dtype="fp16", accumulation_dtype="fp32",
)
program = replace(program, launches=(replace(
    program.launches[0], requires_arch=("wgmma",), residency=1,
),))
result = sight.analyze(
    program, arch,
    options=sight.Options(cache="fast", ii_mode="periodic_best"),
)

“Residency = 1” means one concurrent CTA per SM. We set it explicitly after checking that the compiled kernel permits one.

2. Divide the output, then divide K

Across the GPU

(4,096 / 128) × (4,096 / 128)
= 32 × 32 = 1,024 output tiles

Each tile belongs to one CTA, also called a thread block. A CTA runs on one SM; it is not permanently assigned to a particular SM number.

Inside one CTA

4,096 / 64 = 64 K steps

The CTA keeps its 128 × 128 output accumulator while walking through K. Each step adds another product to that same accumulator.

Inspect a tile and one K step

Ranges use Python’s end-exclusive convention. Sliders inspect the fixed plan; they do not rerun the performance model.

For tile (0, 0), the first step multiplies A[0:128, 0:64] by B[0:64, 0:128]. The next step uses K positions 64:128. After all 64 steps, the output tile contains the full dot products.

3. Write the tile execution plan

The GEMM example builder declares five operation types. It records them for analysis; it does not inspect the compiled CUDA kernel to discover them.

Load A128 × 64 FP16 values → shared memory
Load B64 × 128 FP16 values → shared memory
MMA: multiply and accumulateUpdate 128 × 128 FP32 values in registers
Cast CConvert the final accumulator to FP16
Store CWrite 128 × 128 FP16 values to global memory

Load A, load B, and MMA repeat 64 times. Cast and store run once, after the loop. An epilogue in the builder describes that final work.

Show the builder’s operation sequence
with kb.loop("k", 64, stages=3) as loop:
    kb.copy(A["m", "k"], A_s, name="load_A")
    kb.copy(B["k", "n"], B_s, name="load_B")
    kb.gemm(A_s, B_s, acc, name="mma", ...)
    with loop.epilogue():
        kb.cast(acc, C_r, name="cast_C", actor="epilogue")
        kb.copy(C_r, C["m", "n"], name="store_C", engine="ldst")

This excerpt fixes the loop count to this example and omits optional GEMM arguments. It is a plan-building sketch, not executable GPU code.

The accumulator is distributed across threads. Its logical size is not the kernel’s total register allocation. The factor 2 counts a multiply and an add.

4. Convert work and traffic into resource times

For each operation, TileSight estimates time demanded from each hardware resource. These entries form its resource-time vector. They are modeled service times, not separately measured durations.

Resource time = work / throughput
Memory resource time = bytes handled at that level / its bandwidth share

The run used the repository’s H20().set_to_microbench() constants unchanged:

Why divide by 78? The model has 78 active SMs and one resident CTA per SM. It shares device-wide HBM and L2 rates equally, and converts the summed compute and shared-memory rates into per-SM rates. It does not mean HBM is physically divided into 78 private memories.

Work through one 16 KiB A load

The cache model assigns an average of 324.54 HBM bytes to each A load, while all 16,384 bytes generate L2 read requests and shared-memory writes. Cached reuse explains the different byte counts.

tHBM = 324.5426 / (4.305 × 1012 / 78) = 0.005880 µs
tL2 = 16,384 / (8.123448629 × 1012 / 78) = 0.157316 µs
tSMEM = 16,384 / (19.768320312 × 1012 / 78) = 0.064646 µs
tload A = max(0.005880, 0.157316, 0.064646, 0.064646) = 0.157316 µs

The fourth entry is TMA service. This run has no independent TMA rate, so the implementation uses the shared-memory port rate as a proxy.

These are not three serial journey segments to add. They are demands on HBM, L2, and shared-memory resources. The move-cost model takes their maximum, plus any explicit extra latency. Extra latency is zero in this run. The full loop model then considers resource contention and dependencies between operations.

Why do A and B have different HBM byte counts?

The grid traversal determines reuse. Adjacent output tiles can reuse input tiles through L2. The sampled cache model estimates 324.54 HBM bytes per A load and 1,391.12 per B load, averaged across the grid. These are model estimates, not literal fractional memory transactions or a measured cache trace.

The cache trace is approximate and starts cold. Both loads are L2-limited under these estimated rates, so they receive the same 0.157316 µs completion time.

Show the MMA, cast, and store arithmetic
tMMA = 2,097,152 / (139.22 × 1012 / 78) = 1.174959 µs
tcast = 16,384 / (29.231883 × 1012 / 2 / 78) = 0.087435 µs

Cast is priced as one CUDA instruction unit per value. The code divides the FP32 FMA FLOP/s convention by two to obtain an instruction rate. This is a model approximation, not a dedicated measured cast throughput.

For the store, HBM service is the largest resource time. The plan charges all 32 KiB to HBM and L2 writes; register-read and LD/ST proxy times are smaller.

5. Overlap loading with the K loop

Adding all five costs and multiplying by 64 would be wrong. Output work happens once, and input loads can overlap with the preceding MMA. The three stages supply reusable input buffers.

The solver finds a periodic schedule with an initiation interval, II, of 1.174959 µs. II is the time between starting consecutive K iterations. Here, tensor work sets that interval.

Per iteration: L2 demand = 0.157316 + 0.157316 = 0.314633 µs
Per iteration: tensor demand = 1.174959 µs
Selected II = 1.174959 µs

The solver also checks that data is ready, the accumulator recurrence is respected, and buffers can be reused. It does not choose II from resource totals alone.

This is TileSight’s constructed schedule, not a GPU profiler trace. Blue bars are A then B loads; green bars are MMA. Hover a bar for its modeled start and end time. A model actor is a scheduling role, not an individual SM.

In the first iteration, A starts at 0, B at 0.157316, and MMA at 0.314633 µs. The next iteration starts at 1.174959 µs, so its loads overlap with the previous MMA.

Ttile = initial loads + 64 × II + final cast + final store
= 0.15731644 + 0.15731644 + 64 × 1.17495946

= 76.19317972 µs

The last MMA finishes at 75.512038 µs. Cast finishes at 75.599474 µs, then the store completes the tile at 76.193180 µs.

6. Schedule 1,024 tiles on 78 SMs

The kernel permits one resident CTA per SM. The model therefore has 78 concurrent slots. It assigns the next tile to the earliest free slot.

1,024 = 13 × 78 + 10
Modeled waves = ⌈1,024 / 78⌉ = 14
Tkernel body = 14 × 76.19317972 = 1,066.704516 µs
17827837847857867877887897810781178127813781410

After 13 full waves, ten tiles remain. They still take one tile duration. They do not take 10/78 of that duration, because each must finish all 64 K steps.

This run uses full_wave_costs: even the last ten CTAs retain the full-wave resource shares. “Wave” is the model’s useful grouping here, not a hardware-wide synchronization barrier.

Open the explorer separately · Model configuration and provenance

Full-access calculation, not measured cache counters. This explorer examines all 65,536 A loads and all 65,536 B loads without event sampling. Its mean L2-hit estimates are 96.71% for A and 91.70% for B. L2 capacity is 60 MiB, shared across the GPU. One A or B tile occupies 16 KiB, so that is the capacity equivalent of 3,840 input tiles.

The historical timing calculation above used the fast sampled cache model. A later audit found that its 324.54-byte A estimate undercounts compulsory reads: a cold, uncompressed A matrix requires at least 512 HBM bytes per load on average. The full-access calculation gives 538.72 bytes for A and 1,359.58 bytes for B. Those updated cache estimates are used in this explorer; the original timing results above are retained as recorded.

7. Compare like-for-like timing

1.066705 msTileSight kernel-body prediction
1.101956 msMeasured device kernel duration
3.20% lowPrediction error / measured time

The measured value is the median of 51 Nsight Systems samples with cold-cache preparation. Allocations, correctness checks, warmup, and cache-flush execution are outside those kernel intervals.

TileSight also reports 1.068705 ms when its default 2 µs launch term is included. We use 1.066705 ms for the comparison to device-only kernel duration.

The result supports this specific tile-level model as a useful starting point. It does not prove each substep’s modeled duration: individual instructions, barriers, parts of internal memory traffic, and real cache behavior remain approximate.

The model rates were not fitted to this result. The profile’s clock field is 1,743 MHz, while the GPU ran near 1,980 MHz under load; we kept the existing throughput constants. This is not a fresh hardware calibration.
