1. Choose a workload with little reuse per weight

A16 × 8,192 × B8,192 × 79,872 = C16 × 79,872
FP16 inputs and output · FP32 accumulation

Each element of B contributes to only 16 output rows. B occupies 1.21875 GiB, far more than this H20’s 60 MiB L2 cache. A occupies 256 KiB and can be reused by many output tiles.

Useful work = 2MNK = 20,937,965,568 FLOPs
Ideal traffic = 2(MK + KN + MN) = 1,311,440,896 bytes
Arithmetic intensity = work / traffic ≈ 15.97 FLOPs/byte

This traffic estimate reads A and B once and writes C once. The profile’s compute-to-HBM ratio is 139.22 TFLOP/s ÷ 4.305 TB/s = 32.34 FLOPs/byte. Our intensity is below that ratio, which makes memory bandwidth the expected limiting resource.

≈ 150.39 µs

1.31144 GB / 4.305 TB/s
≈ 304.63 µs

These are lower bounds, not the full TileSight prediction. The full model accounts for per-tile operations and a constructed overlap schedule below. All bandwidths use decimal bytes/s; KiB, MiB and GiB use powers of two.

2. Divide the output, then divide K

Across the GPU

(16 / 16) × (79,872 / 128)
= 1 × 624 output tiles

One CTA, or thread block, owns a 16 × 128 output tile. Every CTA uses the same A rows and a different 128-column slice of B.

Inside one CTA

8,192 / 64 = 128 K steps

The CTA accumulates all 128 products into the same output tile. Its 128 threads form four warps; the warp tile is 16 × 32 × 64.

Inspect a tile and one K step

Ranges exclude the end index. These controls inspect the fixed plan; they do not rerun TileSight. Output tile width is drawn to scale.

There are no invalid rows or columns in these tiles. The 16-row height is an explicit configuration choice, matching the actual kernel.

3. Describe one tile’s execution

The actual CUTLASS kernel uses cp.async input copies and warp-level mma.sync Tensor Core instructions on H20. It accumulates in registers. This differs from the TMA/WGMMA path in the 4K example.

Load A · repeat 128 times16 × 64 FP16 values → shared memory
Load B · repeat 128 times64 × 128 FP16 values → shared memory
MMA · repeat 128 timesUpdate the 16 × 128 FP32 register accumulator
Cast C · onceConvert the final result to FP16
Store C · onceWrite 16 × 128 FP16 values to global memory

TileSight’s builder records these operations and their dependencies. It does not discover the plan from the compiled kernel. There are no scales, quantization steps, bias, or activation functions.

QuantityArithmeticPer CTA
One A load16 × 64 × 2 bytes2 KiB
One B load64 × 128 × 2 bytes16 KiB
Three input-buffer stages3 × (2 + 16) KiB54 KiB shared
FP32 accumulator16 × 128 × 4 bytes8 KiB logical data
Final FP16 output16 × 128 × 2 bytes4 KiB
One MMA step2 × 16 × 128 × 64262,144 FLOPs

Logical accumulator size is not total register allocation. The compiled kernel uses 64 registers/thread and 55,296 bytes of shared memory. The plan abstracts away individual shared-to-register loads, epilogue shared-memory exchanges, barriers, and address calculations.

Show the actual plan-building code

Here m = 16, n = 79,872, k = 8,192 and residency = 4. The full runnable predictor is in the downloads.

kb=KernelBuilder('main',grid={'n':n//128,'m':m//16},threads=128,dispatch_order='linear_block_id',metadata={'kernel':'cutlass_mma_sync_cp_async','block_m':16,'block_n':128,'block_k':64})
A=kb.tensor('A',(m,k),'fp16'); B=kb.tensor('B',(k,n),'fp16'); C=kb.tensor('C',(m,n),'fp16')
As=kb.shared('A_s',(16,64),'fp16',stages=3);Bs=kb.shared('B_s',(64,128),'fp16',stages=3)
acc=kb.fragment('acc',(16,128),'fp32',carried=True);Cr=kb.fragment('C_r',(16,128),'fp16')
with kb.loop('k',k//64,stages=3) as loop:
    kb.copy(A['m','k'],As,name='load_A',engine='cp_async')
    kb.copy(B['k','n'],Bs,name='load_B',engine='cp_async')
    kb.gemm(As,Bs,acc,name='mma',compute_dtype='fp16',accumulation_dtype='fp32')
    with loop.epilogue():
        kb.cast(acc,Cr,name='cast_C',actor='epilogue')
        kb.copy(Cr,C['m','n'],name='store_C',engine='ldst')
program=kb.program(name='gemm_cp_async')
program=replace(program,launches=(replace(program.launches[0],residency=residency),))

4. Convert work into resource times

CUDA’s occupancy query permits four resident CTAs per SM for this compiled kernel. With 78 SMs, the model has 312 concurrent CTA slots. The per-CTA rates below divide the device-wide or summed rates by 312.

Work through one 16 KiB B load

tHBM = 16,384 / (4.305 × 1012 / 312) = 1.187412 µs

These are demands on different resources, not sequential travel times to add. The move-cost model takes the maximum. No extra transfer latency is configured here. The copy-engine cost uses shared-memory bandwidth as a proxy, rather than an independently calibrated cp.async rate.

Why loading A is much cheaper

Each A chunk is only 2 KiB. The selected cache estimate charges its requests to L2, with no HBM charge for A in this run. That gives 0.078658 µs per load. This is an approximate cache-model result; it does not mean a real cold GPU needs no initial A fetch.

tMMA = 262,144 / (139.22 × 1012 / 312) = 0.587480 µs
One B load takes about twice one MMA step.

Cast uses the profile’s FP32 CUDA rate, divided by two to turn the FMA FLOP convention into an instruction-rate proxy. Store is HBM-limited under the model. Both execute only after all 128 K steps.

5. Overlap computation with the next B load

The periodic solver selects an initiation interval, II, of 1.187412 µs. This is the time between starting consecutive K steps. HBM service sets the interval; the 0.587480 µs of tensor work fits inside it.

Per-step HBM demand = 1.187412 µs
Per-step L2 demand = 0.078658 + 0.629266 = 0.707924 µs
Per-step tensor demand = 0.587480 µs
Selected II = 1.187412 µs

The solver also checks dependencies, the accumulator recurrence, and buffer reuse. It then constructs a schedule that achieves this interval within the supplied model.

TileSight’s modeled operation timeline, not a measured GPU trace. Hover over a bar for exact times. Separate load lanes show overlapping in-flight operations; they do not imply a dedicated warp for each lane.

Step 0 loads A at 0, loads B at 0.078658 µs, and starts MMA at 1.266070 µs. At that moment, B for step 1 can start loading. This hides most of the MMA time behind the next B load. Three input-buffer stages allow data to be in flight while earlier data is consumed.

Turn the schedule into one CTA’s time

TCTA = 128 × II + load A + MMA + cast + store
= 128 × 1.187411847 + 0.078658219 + 0.587479730
+ 0.043717745 + 0.296852962
= 152.995425032 µs ≈ 153.00 µs

The 128 × II term covers the repeated B-load interval. The remaining terms are the initial A lead-in, the last MMA, and final output work. This equation is specific to the saved schedule; it is not a universal GEMM formula.

6. Run 624 CTAs in two modeled waves

Concurrent slots = 78 SMs × 4 CTAs/SM = 312
Waves = 624 CTAs / 312 slots = 2
Tkernel body = 2 × 152.995425032 = 305.990850063 µs
Wave 1 · 312 CTAs0 → 153.00 µs
Wave 2 · 312 CTAs153.00 → 305.99 µs

Each SM can host four independent CTAs. They share that SM’s resources; they do not jointly compute one tile. N = 79,872 was selected before measurement so that the grid fills two full waves.

Waves summarize the model’s scheduling cost. The GPU does not execute a global barrier between these two groups. The model separately reports a 2 µs launch term; this page excludes it when comparing with device-only kernel duration.

The low arithmetic intensity, large streaming operand, and high useful-byte throughput support bandwidth-dominated execution. The 3.6024 TB/s value is derived from B’s useful size, not a hardware traffic counter. We did not have access to performance counters for this experiment.

A separately checked bandwidth discrepancy

The saved profiler metadata reports 4.022784 TB/s nominal memory bandwidth for this H20. TileSight’s microbenchmark profile uses 4.305 TB/s, about 7.02% higher. Its source does not record the calibration conditions beside that value.

A CPU-only rerun changes just this rate to the independently recorded board value. The tile plan, occupancy, other rates, and measured result stay unchanged:

Model variantPredictionBelow cold measurement
Original profile · 4.305 TB/s305.991 µs57.273 µs · 15.77%
Recorded board rate · 4.022784 TB/s327.358 µs35.906 µs · 9.88%

This independent rate substitution moves the prediction by 21.367 µs. It is a sensitivity check, not a fitted bandwidth or proof that exactly 21.367 µs of the physical runtime has this cause.

Cold preparation also increases the measured median by 9.760 µs compared with repeated inputs (363.264 versus 353.504 µs). The board-rate prediction remains 26.146 µs below the repeated-input measurement. These comparisons do not isolate additive causes: cache state, traffic, and overlap can interact.

What remains unexplained

A nominal board peak is not achieved kernel bandwidth. The model also omits some instructions and synchronization costs, and reuses aggregate Tensor Core and copy-rate proxies. The evidence does not yet separate actual memory efficiency, copy/compute overlap, barriers, and epilogue cost. Claiming one of them explains the entire remaining gap would go beyond the measurement.

We retained the mismatch. No bandwidth or latency constant was fitted to make the prediction agree. This case is less accurate than the earlier compute-bound examples.

All 1,277,952 output elements matched cuBLAS exactly for the deterministic multiples-of-1/8 input fixture. This validates the intended computation for those inputs; it does not promise bitwise equality for arbitrary floating-point inputs.
