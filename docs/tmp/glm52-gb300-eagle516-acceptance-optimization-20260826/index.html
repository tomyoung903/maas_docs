Definition

Acceptance length includes one non-draft bonus token

For this shape, each verification can accept at most five drafted tokens and then emits one verifier token. SGLang reports their sum as acceptance length. Therefore the draft-only percentage is:

Adraft= ((Laccept − 1) ÷ 5) × 100%

For the formal default-policy baseline, Laccept = 3.75922, so 2.75922 of five drafts were accepted: 55.1844%. The bonus token is not credited to the drafter.

Three acceptance mechanisms—and only one safe alternative

Single-token threshold

single=0.05 adds a deterministic shortcut: accept a proposed token whenever the verifier gives that token at least 5% probability. The default is 1.0.

Accumulated threshold

An accumulated threshold t below 1 raises stochastic acceptance from p to min(1, p / t). It is also distribution-changing; it is not an exact-speculation improvement.

Classical rejection sampling

For a draft token with target probability p and draft probability q, accept with min(1, p / q); on rejection, sample from the positive residual distribution. This preserves the target distribution when the implementation assumptions hold.

Observed result

Rejection sampling improved the 128-row natural gate to 58.80%, but that remains 11.20 percentage points short of the target.

The fixed-128 screen was not a promotion gate.

single=0.05 looked like 72.57% under forced 128-token output, then rose to 88.69% during natural generation. Request 111 changed from 2,851 tokens and stop under the default policy to 128,000 tokens and length. The run was stopped rather than mislabelled as a quality improvement.

Formal validation A

One 4,000-row baseline; candidates had to pass a gate first

Every arm began from a cache flush and reset acceptance counters. The client admitted at most 100 requests per server, used no retries, preserved sampling parameters, EOS behavior, source stop controls, and each request’s original output limit. It stored usage and timing only—never prompts or generated text.

Those source limits were intentionally large: 6 requests allowed 40k tokens, 2,219 allowed 80k, and 1,775 allowed 128k. Normal model stop behavior—not an artificial 128-token cap—therefore determines the natural-output tail.

The acceptance value is the scheduler’s cumulative ratio of accepted tokens to verification forwards since that reset. It is not the latest 40-step logging window: /server_info divides the cumulative counters, and the threshold-update endpoint clears those counters before each arm.

The matched-output load exposed a fatal runtime failure

The same first 512 requests were issued after independent cache flushes, with 128 forced output tokens, 100 maximum in flight, and no retries. The default arm completed. Checkpoint audit

The bundled MTP layer is already BF16

Direct tensor evidence

The NVFP4 config excludes model.layers.78*. Safetensors metadata shows 790 BF16 tensors, 1 FP32 tensor, and no scale-like tensors across layer 78.

Consequence

“Try a BF16 drafter” was already satisfied by the baseline. The official ZAI FP8 MTP reached 52.66%—only 0.19 percentage points over the bundled exact screen—while the Phala W4A-FP8 head was incompatible.

The likely exact-quality bottleneck is alignment between the MTP head and this NVFP4 verifier/runtime, not MTP weight precision alone. A real exact-policy path to 70% needs a better-matched MTP head—most plausibly distillation or fine-tuning against the deployed quantized verifier—not another dtype flag.

Runtime safety

Numerical success does not erase the screening crashes

  • The node-132 pod restarted twice during low-threshold screening. The delayed failure surfaced as a CUDA illegal memory access in DSA CUDA-graph metadata handling and then through the NCCL watchdog.
  • The 4,000-row default baseline and 128-row rejection-sampling gate completed without a restart, but the rejection server restarted once when the 512-row fixed-output load began.
  • The first fatal stack was dsa_backend.py:_apply_cuda_graph_metadata reporting CUDA error: an illegal memory access was encountered on TP3; the NCCL watchdog then propagated the failure.
  • This is evidence of a runtime bug family, not proof that threshold arithmetic itself corrupts memory. Related upstream reports cover GLM-5.2 NVFP4/DSA/MTP CUDA-graph failures.
Deployment gate: no tested candidate passes acceptance, semantics, and runtime-safety gates together. Leave the current deployment unchanged.

Decision

Do not ship a numerical 70% “fix”

  1. Keep thresholds at 1.0. Lower thresholds can satisfy the counter while violating the behavioral goal.
  2. Do not promote rejection sampling for acceptance. It is principled but reached only 58.8% here.
  3. For a real 70% target, improve verifier–MTP alignment. Fine-tune or distill an MTP head against the deployed NVFP4 verifier, or validate a complete matched verifier/MTP checkpoint rather than swapping only the head.
  4. Repeat this gate sequence. Fixed-output screen → natural-output sentinel → first 4,000 requests → node-swapped throughput → quality/tool-use evaluation.
