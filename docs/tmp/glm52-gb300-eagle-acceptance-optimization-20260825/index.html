03 · definitions

What acceptance and RPM mean here

Strict draft acceptance

Astrict = (Ngenerated − Nverify) / (s · Nverify) s is the configured speculative step count. The bonus target token is excluded from accepted drafts.

Engine counters are differenced across all three decode replicas. This is a token-weighted aggregate over the full run, not the median of request-level ratios.

Acceptance length, including bonus

Laccept = Ngenerated / Nverify This includes the one target-generated bonus token per verification. It is not the same quantity as strict draft acceptance.

A 5-step run can have a larger acceptance length but lower strict acceptance because it proposes more draft tokens per verification.

Two output-rate denominators

Issue starts The bounded backlog fills toward 100 in flight.
Saturated window Count valid output tokens completed before the final request is issued.
Issue ends Request 4,000 has been issued; issue-window RPM is now fixed.
Natural drain All remaining uncapped requests finish; full-cohort RPM includes this tail.

The issue-window rate is completion accounting, not a raw kernel counter. The full-cohort rate uses decode-engine generation-token deltas divided by total wall time. Both are valid, but they answer different operational questions.

04 · interpretation

The exact and approximate frontiers are different

Exact semantics

  • 1-1-2: 83.01% acceptance, but issue-window RPM falls 4.12%.
  • 2-1-3: issue-window RPM rises 6.32%, but acceptance is 68.84%.
  • Conclusion: no tested exact point clears both requested gates.

Approximate semantics

  • 0.98: 73.25% acceptance, but issue-window RPM falls 1.89%.
  • 0.97: 70.60% acceptance and issue-window RPM rises 1.28%.
  • 0.95: issue-window RPM rises 2.97%, but acceptance is 68.69%.
Why is aggregate acceptance not perfectly monotonic with the threshold? Relaxing a token-level decision changes which tokens enter the sequence, which changes later draft and target probabilities, stop/tool-call timing, output length, routing, and the token-weighted mix seen by the counter. These runs preserve request settings, not identical generated trajectories. The threshold is locally more permissive; the run-level aggregate need not interpolate smoothly.
What the 0.97 threshold changes

The accumulated threshold is part of acceptance policy. Lowering it can accept a draft token in cases where exact rejection would not. That is an approximation to target sampling, so a higher measured acceptance rate does not establish a better draft model, better weights, or higher target–draft agreement.

This distinction is central: a draft-model improvement should raise acceptance under the same exact policy. The 0.97 result instead trades semantic fidelity for fewer rejected speculative branches.

06 · controlled setup

Experiment contract

Serving topology

  • GLM-5.2 target: NVFP4.
  • Draft quantization: modelopt_fp4.
  • Prefill: PP4 on node 136.
  • Decode: three independent TP4 replicas on nodes 129, 132, and 169.
  • DP, EP, and decode PP disabled for each TP4 replica.

Replay contract

  • Verified filtered Liaoze Europe six-hour dataset.
  • First 4,000 rows in source order.
  • Original request fields and output limits preserved.
  • Bounded backlog, maximum 100 in flight.
  • No retries; every terminal HTTP outcome retained.

Admission-control repair applied to every formal run

The inherited frontend default used an active-prefill token fraction of 64, which produced overload near 524,288 active prefill tokens. Formal paired runs explicitly disabled that hidden fraction limit, retained a 300,000 ms prefill overload threshold, and set prefill maximum running requests to 100. A 100-request synthetic test completed before formal replay.

This repair is not counted as an EAGLE candidate improvement because it was held constant across the promoted baseline and every paired candidate.
07 · limitations

Why the measured pass is not yet a deployment decision

  • Approximate output semantics: accumulated threshold 0.97 can change sampled output. Acceptance is raised partly by policy, not solely by target–draft agreement.
  • Narrow throughput margin: +1.28% issue-window RPM is too small to treat as durable without repeated runs or an online randomized A/B.
  • Failure regression: HTTP 529 outcomes rose from 15 to 22 even though the burst remained bounded and every row was accounted.
  • TTFT trade-off: candidate P50 TTFT rose from 3.70 s to 4.43 s.
  • Long-tail regression: candidate full-cohort RPM was 222.3k, 8.06% below baseline, because its uncapped drain lasted 704.9 s.
  • Trace scope: the full unfiltered dataset was unavailable on the four authorized nodes, so this uses the verified prompt-token-less-than-300k file.
  • Generated paths differ: source requests are paired, but sampling and approximate acceptance do not guarantee identical outputs or output lengths.
08 · next decision

Use 0.97 only in a guarded A/B; keep improving exact acceptance

Short-term validation

  1. Repeat baseline and 0.97 at least three times with shuffled, fixed request cohorts.
  2. Run semantic regression checks on tool calls, stop behavior, and answer quality.
  3. Gate on issue RPM, TTFT, HTTP 529 rate, and full-cohort drain—not acceptance alone.
  4. Use a small online canary before any broad rollout.

Long-term fix

  1. Improve or retrain the GLM-5.2 EAGLE draft weights for this target checkpoint.
  2. Re-test exact 2-1-3 under the same workload after each draft change.
  3. Investigate the bounded early 529 burst independently of EAGLE acceptance.
  4. Prefer an exact-policy point that clears 70% and preserves the 2-1-3 throughput gain.
Production bar: do not promote solely because this one run crosses 70%. The experiment proves a plausible operating point, not a stable quality-preserving production improvement.
