1. Experiment contract

Everything that could move the acceptance denominator was pinned. The only intentional policy changes were accumulated acceptance threshold or classical rejection sampling.

Server

NVIDIA GB300 ×4 on gpu-worker-gb300-136; TP4 / DP1 / EP1 / PP1; FP4 target and bundled FP4 MTP draft; FP8 KV cache; DSA; max running requests 128; replay backlog capped at 100.

Dataset

Unfiltered verified Liaoze Europe six-hour trace: 36,773 rows. SHA-256 a64a31f…e1cbb. Prompts, tools, source IDs, generated text, and raw errors were never persisted by the replay client.

Cohort A

26,923 requests: temperature 1.0, top-p 0.95, no top-k. These rows include source output caps up to 128k tokens.

Cohort B

9,701 requests: temperature 0.7, top-p 0.7, no top-k. Another 149 trace rows use other policies and were excluded from this A/B.

Pairing guarantee. Every A/B pair used an identical cohort offset, row count, source-prefix hash, and set of invalid request fingerprints. No retries were used. Invalid rows were deterministic HTTP 400s and were never silently replaced.

Threshold 0.38 is a failed optimization despite 75.81% acceptance. On identical inputs, total output rose 61.59%, elapsed time rose 96.29%, output-token rate fell 17.68%, and one request hit the full 128,000-token limit. That is behavioral drift, not free draft efficiency.

Threshold 0.44 is the least aggressive useful point, but its acceptance moved from 72.79% on the primary slice to 65.20% here. A single favorable slice is therefore insufficient to claim a stable 70% service-level acceptance rate.

Temperature 0.7

65,536 tokens in each arm. Acceptance rose 5.04 points, but output-token rate changed only 0.24% (15,876 → 15,915 tok/min).

Why the speedup is modest. More accepted draft tokens reduce target verification work, but this service still pays long-context attention, MTP drafting, target verification, scheduling, and communication. Acceptance percentage is not a direct multiplier on end-to-end throughput.

Safe does not mean high acceptance. Rejection sampling fixes the sampling semantics problem of relaxed thresholds; it cannot make a mismatched draft distribution resemble the target. The measured result points back to draft-model quality, not to a missing acceptance trick.

8. Stability, crash recovery, and release

The experiment completed, but the runtime image is not stable enough for a production recommendation under this workload.

Two delayed crashes

The target-only deployment restarted once and the rejection deployment restarted once. Both faults surfaced after a long-tail arm, before the next replay sent any request.

Same failure path

dsa_backend.py::_apply_cuda_graph_metadata reported CUDA illegal memory access; NCCL watchdogs then aborted TP ranks. This is a runtime/DSA CUDA-graph defect, not evidence that threshold arithmetic itself crashed.

Recovery integrity

Each interrupted arm had no output directory and zero sent requests. The pod restarted automatically; health and live 5-1-6/policy state were revalidated; the same arm ID and source slice were rerun from row 1.

Resources released

At 05:13 CST all experiment Deployments, Services, Pods, and ConfigMaps were absent. DCGM showed GPU utilization 0 and framebuffer used 0 on GPUs 0–3.

9. How to read acceptance

avg_spec_accept_length includes the final target/bonus token. With five draft opportunities, strict draft acceptance is:

strict acceptance = (avg_spec_accept_length − 1) ÷ 5 × 100%

For example, accept length 4.64 means about 3.64 accepted draft tokens plus one target/bonus token, or roughly 72.8% strict draft acceptance. This definition was applied uniformly to every arm.

What each experiment answers

  • Natural output: what the service does on real request controls, including changes in stopping trajectory.
  • Fixed 128 output: whether more acceptance improves output-token throughput when successful requests perform equal generated work.
  • Rejection sampling: whether a semantics-preserving acceptance rule helps these two stochastic cohorts.
  • Disjoint replication: whether a promising threshold survives a new source slice and reversed arm order.

Client TPOT is derived from streamed deltas and completion-token usage. It is diagnostic for these concurrent batch replays, not an isolated single-request latency benchmark.

10. Recommendation

  1. Do not promote threshold 0.38. It wins the acceptance metric by changing outputs and causing a 128k-token runaway.
  2. Treat threshold 0.44 only as an approximate research candidate. It is the least aggressive point tested with useful fixed-work gain, but temperature-1.0 acceptance ranged 65.20%–72.79% and quality equivalence was not measured.
  3. Do not enable rejection sampling merely to chase acceptance. It is principled, but measured 54.94% / 69.07% here.
  4. The real route to stable 70–80% is a better draft. Validate a newly trained/compatible GLM-5.2 MTP checkpoint with exact semantics, then repeat these cohort-separated and fixed-work controls.
  5. Upgrade or patch the DSA CUDA-graph runtime before production A/B. Two delayed illegal-memory failures invalidate a reliability claim even though the harness recovered cleanly.
Decision: the goal was achieved as a numerical experiment, not as a production-ready optimization. Keep exact policy for service safety; use 0.44 only behind explicit quality evaluation, output caps, and rollback guardrails.
