Resolved runtime state worth checking

  • FCFS scheduling; overlap scheduling resolved to disabled for this PP configuration.
  • Each node launched the same command with NODE_RANK=0 or 1; deterministic-inference mode was not enabled.
  • Radix cache enabled with LRU eviction; chunked prefix cache enabled; page size 64.
  • Hierarchical cache enabled with direct I/O, page-first-direct layout, write-through policy, ratio 1.2, and no storage backend. This run therefore observed device and host cache tiers, not a storage tier.
  • Decode CUDA graph disabled; prefill CUDA graph remained enabled in breakable mode.
  • DSA/TRT-LLM prefill backend and FlashInfer TRT-LLM routed MoE were selected by the pinned image.
  • No speculative decoding, EAGLE, data-parallel attention, disaggregation, or separate decode worker.
4. Warm-up, cache reset, and measured initial state
  1. Start both server nodes and wait for the built-in warm-up and readiness sequence to complete. The leader became healthy at 06:29:08 UTC.
  2. Send one deterministic real-trace smoke request (source ordinal 793). It had 54,011 prompt tokens and one output token; PP0 showed thirteen full 4,096-token chunks followed by a final chunk.
  3. After the smoke request completed, call POST /flush_cache?timeout=30.
  4. Require HTTP 200 and “Cache flushed successfully!” from every stage PP0 through PP7. The recorded flush completed at 06:29:36 UTC.
  5. Start the formal replay only after the flush. The first formal request was admitted at 06:30:31.516 UTC.

This ordering preserves process, model, communication, and kernel warm-up while removing the smoke request’s prefix-KV state. No synthetic KV cache was constructed. The measured cache hit rate then emerged naturally from repeated prefixes in the real request stream, in original file order.

The smoke wrapper initially treated the HTTP-200 text “Cache flushed” as a false negative because it searched for the literal word “success.” Before formal traffic began, the server logs independently confirmed “Cache flushed successfully!” on PP0–PP7. The retained wrapper now accepts the endpoint’s actual wording; no second smoke request was sent.

6. Load algorithm and exact formal replay command

Bounded backlog means the client reads records in source order, fills an 80-slot asynchronous HTTP pool, and admits the next record whenever a slot completes. It does not preserve production inter-arrival gaps. This intentionally keeps pressure on the server so queueing can form, while the internal-TTFT metric separately removes scheduler queue time.

python3 "$run_root/scripts/replay_trace.py" \
  --run-id glm52-gb300-pp8-realtrace-chunked4k-capacity-20m-20260822 \
  --source /mnt/disk0/tom/datasets/glm52-liaoze-europe6h/requests_last6h_raw.prompt_tokens_lt_300000.jsonl \
  --expected-source-sha256 9cb06790675e6cd3b3cf1fcca8232f82f36d5002a86351c6510c1c3bb8c77acb \
  --expected-records 35744 \
  --zero-cache-when-details-omitted \
  --endpoint http://127.0.0.1:30000/v1/chat/completions \
  --prometheus-url http://127.0.0.1:30000/metrics \
  --model zai-org/glm-5.2 \
  --cadence bounded-backlog \
  --max-inflight 80 \
  --request-timeout-seconds 3600 \
  --issue-duration-seconds 1200 \
  --drain-timeout-seconds 3600 \
  --metrics-interval-seconds 1 \
  --output-dir "$run_root/client/formal-capacity-20m"

  2. Place the exact source JSONL on the experiment node. Verify both sha256sum and the 35,744-record count before starting the server.
  3. Copy launch_server.sh, run_formal_replay.sh, and replay_trace.py into the recorded run-root scripts/ directory.
  4. Launch node rank 1 and node rank 0 with stdout/stderr captured in their node-local worker and leader logs. Wait for readiness; do not include startup or model loading in the formal window.
  5. Run the representative long-prompt smoke request, wait for completion, flush the cache, and require success from every PP rank.

10. Scope limits for similar experiments
  • This was a standalone, unified SGLang server. It omitted Dynamo registration, prefill/decode disaggregation, Mooncake KV transfer/storage, and a separate decode worker.
  • This was a saturated bounded-backlog capacity run, not a replay of original production arrival times. Use --cadence original only for a different question, and label that result separately.
  • The one-token output contract isolates prefill-shaped work and makes TPOT unavailable. Do not compare its request rate directly with a long-output decode workload.
  • The 83.095% cache hit rate is an outcome of the pinned real-request order after an empty-cache start. Reordering, shuffling, truncating, warming, or resetting between requests changes the workload.
  • This PP8/4K run changes both topology and chunk budget relative to the retained PP4/8K report. A causal one-variable A/B requires holding one of those dimensions fixed.
  • The source body is privacy-restricted and is intentionally absent from this public page. Internal reproduction requires access to the pinned file whose byte count and SHA-256 are recorded above.
