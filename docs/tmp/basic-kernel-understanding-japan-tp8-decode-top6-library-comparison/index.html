Answer first

The bottleneck changes from launch-heavy MoE/collectives to sparse MLA plus larger matrix work.

At B = 1 and 10, fused MoE is rank 1 and small-message custom all-reduce is rank 2. At B = 100, FlashInfer's fused all-reduce + residual + RMSNorm reaches rank 1. At B = 200 and 500, sparse FP8 MLA is rank 1. The backend sources explain the two sharpest transitions: both custom all-reduce families change from one-shot to two-shot algorithms as payloads grow, while DeepGEMM changes tile specialization.

Controlled-comparison limit. B = 1, 10, and 100 use 4,096-token contexts; B = 200 and 500 use 832-token contexts. Any trend crossing that boundary combines batch and context changes.

Scope & method

Exactly what was ranked

BoundaryOne complete, graph-aligned useful decode generation for each batch; post-finish cleanup excluded.
MetricCUDA kernel residency summed across all eight TP ranks and grouped by exact demangled raw name.
ShareEach raw-name subtotal divided by all useful-step kernel residency across eight ranks—not by graph wall time.

The numbers are read from the normalized sidecar behind the source page. “Top six” therefore means six exact symbols, not six semantic modules. A backend may contribute more than one specialization, and related symbols outside the top six are not silently merged.

One-step repeatability limit. Each configuration contributes one selected CUDA-graph generation—one computed decode token per sequence. It is a valid snapshot, but it contains no distribution across steps. Repeating steady decode can change context-scan work, routed-expert balance, TP-rank skew, clocks, and overlap. At B = 100, fused MoE and FP8 quant differ by only 0.063 ms of eight-rank residency, so their #2/#3 order is not a stable conclusion until a repeated-step run reports a median and spread.

Comparison judgment

The rank transition is directionally expected: each added sequence contributes another selected-KV attention problem. Backend or literature

Template Pattern 1 is kARResidualRMSNorm, not MLA attention. FlashInfer's one-shot Lamport path pushes the complete payload to peer buffers and polls locally; its two-shot path partitions tokens across ranks, reduces each partition, broadcasts results, then applies the fused epilogue. The library exposes an explicit one-shot/two-shot choice and size heuristic.

The one-shot symbol ranks 3, 3, 1, and 2 from B=1 through B=200. At B=500 the symbol changes to two-shot synchronization and remains rank 3. Total launches stay at 1,240, so the increasing mean duration reflects larger token payloads rather than more model invocations.

Comparison judgment

This is the cleanest library-consistent transition in the sweep. The trace shows the same size-regime crossover encoded by FlashInfer: one shot for smaller payloads, two shot for the largest batch. The legacy category label attention_mla should not be used to infer the operation.

SGLang Triton fused MoE GEMM

Multiply routed token blocks by expert matrices after token sorting and expert-block padding.

B=1: #1, 14.228 msB=10: #1, 33.489 msB=100: #2, 66.952 msB=200: #3, 57.091 msB=500: #2, 109.570 ms

Backend or literature

SGLang's Triton kernel maps program IDs onto expert-conditioned matrix tiles, reads sorted token IDs and expert IDs, and groups output tiles to encourage L2 reuse. The implementation can use FP8 W8A8 and multiply router weights in the kernel. MegaBlocks provides the broader literature analogue: shape-irregular MoE work is re-expressed as blocked sparse computation rather than padded dense work.

What this trace shows

Rank 1 at B=1 and B=10, rank 2 at B=100, rank 3 at B=200, and rank 2 at B=500. Launch count is fixed at 1,200 while mean duration rises from 11.86 µs to 91.31 µs.

Comparison judgment

This is expected batch scaling for routed expert GEMMs: larger batches supply more rows per expert and increase work per launch. More rows can improve tile utilization even while absolute kernel time rises. Nsight Systems residency alone cannot establish GEMM efficiency; an NCU counter run or shape-matched backend benchmark is required for achieved TFLOP/s.

SGLang custom TP all-reduce

Exchange BF16 TP activations over peer-accessible buffers with a low-latency one-shot or bandwidth-oriented two-shot algorithm.

Backend or literature

The capture's one-shot push kernel writes each rank's full input to every peer and then polls/reduces local peer buffers. The two-shot kernel assigns each rank a partition, reduces that partition, and broadcasts it. Current SGLang retains message-size thresholds for selecting one-shot push, one-shot pull, or two-shot paths.

What this trace shows

The one-shot push symbol is rank 2 at B=1 and B=10. The two-shot symbol replaces it at B=100, B=200, and B=500, ranking 5, 4, and 4. There are only 16 aggregate launches—two per TP rank—so each launch is long and highly visible.

Comparison judgment

The algorithm switch agrees with collective-library practice: latency-oriented replication is attractive for small messages; partitioned reduce/broadcast avoids replicating all work for larger messages. Compare against NCCL with bus bandwidth, message bytes, and rank skew—not MFU or MBU.

What this trace shows

Comparison judgment

The specialization change is exactly what a JIT GEMM backend should do as the M dimension grows. Compare each symbol against the matching DeepGEMM shape and configuration; a repository headline such as peak H800 TFLOP/s is not a baseline for these decode GEMMs.

Backend or literature

PyTorch's sbtopk namespace means single-block TopK. The CUDA kernel performs radix selection, then two gather phases: values strictly beyond the threshold first, followed by enough values equal to the threshold to fill k. Prefix scans determine output positions.

What this trace shows

Ranks 4, 5, 6, 6, and 6 across the sweep. Launch count is fixed at 1,800; total residency rises modestly from 9.17 ms to 15.27 ms while mean launch time grows from 5.10 µs to 8.49 µs.

Comparison judgment

This is a persistent launch-count tax rather than the dominant scaling wall. Larger batches expose more independent slices and GPU parallelism, so time does not grow in proportion to B. Optimization should target fusion or fewer routing stages only after the larger attention, MoE, and collective costs.
