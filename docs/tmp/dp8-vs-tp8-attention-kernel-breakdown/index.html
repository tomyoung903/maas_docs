How the two runs used identical prompts

There were two different caches. The benchmark reused a serialized CPU-side prompt dataset; the serving KV cache was flushed before each measured run.

Prompt dataset cache: intentionally reused

DP8 generated 32 records with seed 424242 and wrote a cache whose key encoded seed, group count, lengths, and tokenizer. DP1 printed Loading cached generated input data for that exact cache file.

The raw JSONL independently matches: both runs contain the same 32 input lengths and the same total of 2,560,473 input tokens.

Server KV cache: intentionally not reused

Both benchmark commands used --flush-cache. Therefore DP1 did not inherit DP8’s attention KV entries. Each topology had to process and transfer its own request contexts.

“Cached prompts” means reproducible workload generation, not a cache-hit benchmark.

How concurrency 32 was guaranteed—and what was not

The client-side issue policy was deterministic: all requests became eligible immediately, and a semaphore allowed at most 32 in flight.

request-rate=infNo Poisson delay: all 32 request coroutines are released at benchmark time zero.
→
max-concurrency=32The client permits all 32 requests to remain in flight simultaneously.
→
Observed peak = 32The benchmark’s recorded max_concurrent_requests equals 32 in both runs.
This guarantees 32 client requests in flight, not a perfectly rectangular decode batch of 32. Two PP4 prefill workers finish long 80K contexts at different times. Requests can therefore join decode in waves, which is one reason TPOT and aggregate output throughput need not move together.

The topology change inside one decode layer

MoE and dense projections remain TP8. The main change is whether attention owns independent request subsets per GPU or shards one request’s attention work across all eight GPUs.

DP8 attention

At a decode step, rank r owns a subset Br of active requests. Its MLA attention reads only those requests’ local KV pages and produces complete attention outputs locally.

Br⊂B, disjoint across ranks
attention work/rank≈|B| / 8 when balanced

TP8 attention, no DP attention

All ranks participate in each active request. Attention projections and heads are sharded, then partial results must be combined before the next replicated or tensor-parallel stage can consume them.

ot=combine(ot,0, …, ot,7)
synchronization=collective communication on the TP group

Why mem-fraction-static=0.95 failed for no-DP attention

Static memory reservation happens before CUDA graph capture. Reserving 95% for weights, KV pools, and static buffers left too little unreserved memory for graph-private allocations in TP8 attention mode.

Mstatic≈fstatic · MGPU
Mfree-for-graph=MGPU − weights − KV/static pools − runtime allocations
failure point=460 MiB free < 2.81 GiB requested
after fstatic = 0.90=9.32 GiB free after graph capture
This is a capacity/startup fix, not a demonstrated decode speed trick. Once both runs have captured their graphs and the 32-request working set fits, a smaller KV pool should not directly make attention arithmetic 24.7% faster. It mainly reduces maximum cache capacity.

Why custom all-reduce failed and why NCCL matters

No-DP attention activates TP communication paths that DP attention can avoid. During graph capture, SGLang loaded a JIT-compiled custom-all-reduce shared object; that object failed dynamic linking because the CUDA Driver API symbol cuPointerGetAttribute was unresolved.

TP8 attention pathCross-rank partial outputs require a collective combine.
→
Custom AR library loadedJIT shared object expects a CUDA Driver API symbol at runtime.
→
Dynamic-link failureSchedulers exit with code 127 before serving starts.

The supported workaround, --disable-custom-all-reduce, routes those collectives through NCCL. NCCL is correct, but its launch protocol, synchronization, and data path can be slower than a tuned intra-node custom reduction for small decode tensors.

This workaround can inflate the observed DP8 advantage. DP8 did not need the failing TP-attention custom-AR path, while the no-DP baseline paid NCCL collective cost. The experiment therefore measures “DP8 as configured” versus “TP8 attention with NCCL fallback,” not versus an ideal working custom-AR baseline.

Best supported conclusion: memory headroom does not explain the speedup. DP attention’s reduced attention-side work/communication is a credible cause, and the NCCL fallback probably makes the no-DP baseline slower, but the current artifacts cannot divide the 3.26 ms delta between those effects.
