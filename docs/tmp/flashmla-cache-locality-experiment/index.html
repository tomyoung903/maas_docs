FlashMLA Cache Locality: What Was Actually Measured

A synthetic, one-kernel experiment changes only the selected KV addresses and observes L1, L2, and HBM traffic. This page keeps hardware measurements, deterministic input construction, and causal interpretation visibly separate.

Answer First

The numbers and the explanation come from different evidence classes. Conflating them makes the result sound more certain—or more production-like—than it is.

Measured

Cache and DRAM counters

Nsight Compute measured L1 global-load hit rate, L2 read hit rate, L2 traffic, and physical HBM traffic on a real H200. Those table values are not calculated from a cache model.

Analysis

Why the counters changed

The statements “the 64-record case benefits primarily from L2” and “the one-record case benefits primarily from L1” are interpretations supported by the controlled address change and measured counters.

Defensible conclusion: this FlashMLA kernel uses both L1 and L2, and increasing selected-record locality sharply reduces HBM traffic in this controlled setup.
Not a production measurement: these are not online cache-hit rates, not a real request distribution, and not a latency benchmark. The experiment deliberately creates artificial address reuse to expose cache behavior.

The Four Address Patterns

Each pattern still executes 204,800 logical selections and the same FlashMLA arithmetic. What changes is how many distinct physical records those selections revisit.

Logical work versus unique data: all four cases request the same 204,800 record references. The unique cases touch 134.3488 MB—larger than the reported 60 MiB L2—while the 64-record and one-record footprints are only 4.1984 MB and 65.6 KB. The hot cases preserve the kernel’s conversion and Tensor Core work while introducing deliberate address reuse.

How to Read L1, L2, and HBM Together

The two hit percentages are conditional measurements with different denominators. They are not three pieces of a pie, and they must not be added or multiplied to reconstruct the HBM byte count.

First opportunity

Per-SM L1TEX

The reported L1 value covers sectors from ordinary LSU global loads. An L1 hit completes that load near the requesting SM.

→
Traffic seen at L2

GPU-wide L2

The L2 percentage asks how many read sectors presented to L2 hit there. Its traffic mix also includes paths not represented identically by the L1 metric.

→
Off-chip service

HBM3e

The DRAM counter measures physical bytes for the whole kernel, including Q, indices, metadata, transaction granularity, writes, and remaining misses.

l1tex__t_sector_pipe_lsu_mem_global_op_ld_hit_rate.pct

Hit rate for global-load sectors issued through the LSU and served by L1TEX. TMA traffic is not included in this exact counter.

lts__t_sector_op_read_hit_rate.pct

Hit rate among read sectors observed by the L2 subsystem. It is conditional on traffic reaching L2.

dram__bytes_read.sum

Total physical bytes read from HBM by the profiled main-kernel invocation across all of its data paths.

Incorrect reading: “95.34% hit L1 and 25.33% hit L2, therefore 120.67% hit cache.” The denominators differ, so this arithmetic has no meaning.

What the Counter Patterns Suggest

The observations below are analysis grounded in the controlled input change and counter response. They are not additional counters.

Analysis

64 records: L2-centered reuse

L1 stays near 19%, but the L2 read hit rate rises to 87.66% and HBM reads fall to 13.008 MB. The private 64-record working sets are repeatedly reused across work that does not remain entirely in one small per-SM L1 footprint, while the GPU-wide L2 can retain much of the active data.

Analysis

One record: L1-centered reuse

L1 reaches 95.34%, so most ordinary global loads finish before L2. The 25.33% L2 rate describes only the smaller and differently composed traffic stream still reaching L2; it is not evidence that caching failed.

Analysis

Ordered versus random

Both visit 204,800 unique records. Ordered access modestly improves L1/L2 hit rates and lowers HBM reads by 7.9%, consistent with better spatial locality and memory-transaction behavior rather than repeated-record reuse.

Analysis

The source supports the mechanism

The pinned kernel emits ordinary KV loads with L1::evict_last and L2::128B or L2::256B prefetch hints. These are hardware hints, not an explicit L2 allocation or residency guarantee.

Strongest claim: address reuse caused a large, measured reduction in physical HBM traffic, accompanied by cache-hit changes consistent with L2 reuse for the 64-record set and L1 reuse for the single-record set.

Limitations and Guardrails

The experiment is useful because it is controlled—not because it perfectly imitates production.

Profiler replay

Each memory report used four passes. Cache state may carry across profiler passes, so the percentages are comparative diagnostics rather than pristine cold-cache statistics.

No explicit cache flush

cache_thrash_mib was zero. The profiler explicitly warned that GPU caches were uncontrolled.

Unmodified clocks

GPU clocks were not locked by the profiler. The counters establish traffic behavior; these runs should not supply headline latency.

Synthetic values

KV numerical values were zero and Q was seeded random BF16. This isolates address service but does not represent actual model semantics.

Not a TP8 run

Only one H200 executed. The first 8 of 64 query heads were active and the remaining 56 were zero, so no cross-GPU execution or communication was measured.

Main kernel only

The filter captured flash_fwd_splitkv_mla_fp8_sparse_kernel. The separate combine kernel’s cache behavior is not measured here.

Whole-kernel bytes

HBM and L2 traffic include Q, indices, metadata, output traffic, prefetch granularity, and transactions—not just the 656-byte useful KV records.

Use the result for: proving cache participation, comparing controlled locality patterns, and understanding why a small working set can avoid HBM reads. Do not use it for: quoting an online L2 hit rate, predicting production latency, or claiming that a particular KV line is pinned in cache.

Profiler command template

The four reports used the same launch filter and profiler controls; only --layout changed.

ncu \
  --kernel-name regex:.*flash_fwd_splitkv_mla_fp8_sparse_kernel.* \
  --launch-count 1 --cache-control none --clock-control none \
  python3 benchmark_flashmla_gap.py \
    --batch-size 100 --valid-keys 2048 --kernel-topk 2048 \
    --q-heads 64 --logical-q-heads 8 --kv-values zero \
    --layout <random|ordered|hotset64|hotset1> --profile-one
