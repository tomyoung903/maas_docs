Does real NVLink 5 reach 900 GB/s?

A normalized collective score can nearly match 900 GB/s. Direct active-copy payload reaches about 89–91% in public examples, while real communication kernels lose more to synchronization and work around the transfer.

The public sources do not decompose every percentage point of the pairwise-copy gap. NVIDIA's own guidance shows that measured payload depends on copy-engine and endpoint efficiency, message size, alignment, bytes in flight, vectorization, and software tuning. Application paths then add launch, layout, queue, and synchronization costs.

The closest detailed official evidence is GB200, not our GB300. Both use the same 900 GB/s-per-direction NVLink 5 fabric rating. Even the measured-copy substitution adds only 7.8 ms; it cannot create a two-second delay. NCCL busbw is a derived collective normalization, so its near-900 result is not contradictory.

Why our P/D boundary is much slower

The decisive correction
  • 27.741 GB/s is workload production: 30,119,736 prompt tokens/min × 55,224 bytes/token ÷ 60 = 27.722 GB/s; page rounding explains the final 0.07%.
  • The 900 GB/s peak assumes one large, aligned, continuously active flow. Our Mooncake path uses 8K chunks, page/layer scatter-gather work, queues, polling, and four-PP-rank completion.
  • All four PP sources share one DPA GPU's 900 GB/s ingress; they do not receive 900 GB/s each. The slowest PP acknowledgement gates decode readiness.
  • kv_transfer_speed_gb_s also mixes all-chunk bytes with a fallback timer beginning after final-chunk submission, so it is not active wire bandwidth.

Formal P→D run: 2,048 requests · concurrency 80 · 189.431 s · 5,255.059 GB page-rounded payload · HTTP TTFT p50 6.054 s · per-rank final-drain mean 0.632–0.636 s. No retained counter isolates active Mooncake or NVLink time.
