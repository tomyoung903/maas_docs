Does online DPA routing actually balance the ranks?

The alarming running-request vector is real—but incomplete. Once decode preallocation and transfer queues are restored, the request distribution is much closer to balanced. Once the router's active-block term is added, its own modeled base costs are almost flat. Physical KV headroom, however, remains sharply uneven.

Verdict

Yes, the snapshot substantially respects the deployed router's balancing objective. It does not equalize the visible running-request counts. It balances a broader state: active requests across the decode pipeline plus active KV blocks. Reconstructing that base score yields only 1.30% coefficient of variation and a 1.038× max/min ratio across the eight ranks.

That is not the same as proving equal real step time. The timing coefficients came from a one-hot GLM-5.2 microbenchmark, while this is an all-ranks-active GLM-5.3 deployment. The page therefore treats milliseconds as a model translation, not an online measurement.

The live command line contains SGLang --load-balance-method total_tokens, but normal online requests arrive with an externally chosen DP rank. That direct rank bypasses SGLang's local load-balancer method.

The deployed objective explains the remaining count skew

The router does not minimize request count alone. It adds a concave request-count penalty to the rank's active decode blocks. For a particular incoming request, it also adds blocks not already covered by prefix overlap.

si(r) = bi + p(ni) + ai(r) · request-conditioned score in 64-token block equivalents
p(ni) = 6749ni − 76ni2 · fitted region through 32 active requests

bi is the router's active-decode-block ledger, ni is its active-request count, and ai(r) is the incoming request's additional active footprint after prefix overlap. The reconstruction below shows the base state before the request-specific final term.

The cleanest counterexample: ranks 1 and 2 both showed 11 running requests. Their full-pipeline counts were 19 and 18, and their reconstructed router base scores were similarly close—165,872 and 161,984 blocks. Yet their physical KV headroom was 27.1% versus 0.50%. Request/cost balance alone is therefore not a sufficient hard headroom guarantee.

This was not isolated: among the 92 high-load samples, at least one rank had less than 1% physical headroom 16 times and less than 5% headroom 43 times. The minimum observed free capacity was 1,600 tokens.

Why the 0.96 ms result must remain “fit-implied”

The coefficients are real and the isolated fit was strong. The experiment geometry, however, differs from the production geometry in exactly the dimension that synchronized DPA makes important: sibling-rank occupancy.

Evidence and method

The production inspection was read-only. No request traffic was generated, and no workload, router, dashboard or cluster object was changed.

  • Population: Taiguo cluster, namespace maas-prod-zhipu, DGD glm53-nvfp4-gb300-pp-dev, decode group 3, ranks 0–7.
  • Snapshot: Prometheus evaluation at 2026-08-31 06:01:42 Beijing time. SGLang source scrapes were 06:01:37.508 and 06:01:38.297; paired frontend router state was scraped at 06:01:38.712.
  • SGLang gauges: running requests, decode preallocation queue, decode transfer queue, KV available and KV used tokens.
  • Dynamo gauges: frontend worker active requests, active decode blocks, per-candidate score histograms and rank-labeled selection counters.
  • Live configuration check: 2026-08-31 14:48–14:50 Beijing. The same no-restart frontend and group-3 processes had been running before the snapshot.
  • Router implementation: Wang Siqin's Dynamo MR !122; model commit 56ebc55e, merged as e747dd98.
  • Historical context: recovered from the exact optim_exp5 Codex session. The separate GLM-5.2 real-trace page is contextual only.

Important limitations
  • The reconstructed base score excludes the incoming request's prefix-dependent additional active blocks.
  • Router active blocks and scheduler KV-pool used/free tokens have different cache and lifecycle semantics.
  • The fit-implied step values are not Nsight measurements or per-rank online latency gauges.
  • Running-request gauges describe scheduler batch state, not GPU occupancy or per-rank kernel duration.
  • To validate causality, hold sibling occupancy and group totals fixed, place the same request on each candidate rank, and measure the incremental group critical path.
