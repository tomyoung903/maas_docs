01 · Root cause

Three bubbles, not a weak GEMM

The comparison is one PP8 versus a mathematical 2× of one measured PP4. Two PP4 replicas implicitly include two independent request frontends.

1

Frontend starvation

One tokenizer/HTTP process could not prepare full 8K work quickly enough for a pipeline advancing nearly twice as fast. Baseline batches averaged only 7,629 tokens.

HTTP + tokenizer→PP8
2

Useless output circulation

A pure middle prefill chunk cannot emit a client token, yet its result object traversed the PP output ring. A guarded skip removes only this semantically empty path.

P0P1P2P3P4P5P6P7
3

Last-rank synchronization

With async depth 0, output preparation happens after launching the current batch and becomes exposed control delay. Depth 1 adds one slot so older output processing overlaps current GPU work.

CPU/result work overlaps the next forward
Bubble = (P − 1) / (P − 1 + M)

Directionally relevant, numerically misapplied here. This formula assumes a finite train of M equal-duration microbatches followed by a pipeline drain. The inference scheduler continuously interleaves chunks from many requests and does not drain between requests, so “one request has 10 chunks” is not the scheduler’s M. The measured last-rank idle fraction—22.47% before and 10.46% after—is the defensible bubble evidence for this workload.
