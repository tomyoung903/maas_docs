02 · Minimal scaling model

The cadence predicts the TPM ratio

This is a measured effective model, not a claim that every layer takes identical time. It asks how much of a stage scales with layer count and how much repeats once per batch.

Observed stage cadence

PP4: 20L + C = 138.228 ms
PP8: 10L + C = 71.014 ms

Here L is effective per-layer time and C is the effective once-per-batch stage floor.

Solved from the two measurements

L = 6.721 ms / layer
C = 3.800 ms / batch

The fixed term includes exposed portions of scheduler work, handoff, stream backpressure, and result processing.

Why exactly 2× is missed

ideal half of PP4 = 69.114 ms
actual PP8 = 69.114 + C/2 = 71.014 ms

The strict target assumes C also halves. It does not: one PP8 stage still schedules and retires one batch. The predicted cadence attainment is 69.114 ÷ 71.014 = 97.324%, almost exactly the measured TPM attainment of 97.271%.

06 · Interpretation

Why one PP8 is not exactly two PP4s

The arithmetic target is useful, but it is deliberately stricter than what pipeline strong scaling guarantees.

PP8 halves layer work, not batch machinery.

Two independent PP4 replicas each process a 20-layer stage every ~138 ms. One PP8 processes a 10-layer stage every ~71 ms. The layer-dependent portion nearly halves; a once-per-batch floor remains. That floor costs about 1.90 ms relative to the ideal half-cadence and quantitatively predicts the observed 97.27% TPM ratio.

So the remaining gap is best described as pipeline strong-scaling overhead: repeated Python scheduling, stream/backpressure boundaries, activation/output handoff, and result retirement. It is not cache-token arithmetic and not one blocking NCCL kernel.

If exact 2× matters

  1. Reduce or move per-rank scheduler work out of Python.
  2. Batch/control-plane handoffs rather than only caching tensor schema.
  3. Decouple result retirement from the next stage-service interval.
  4. Re-profile after each change; tuning GEMM tiles is not the first lever.
