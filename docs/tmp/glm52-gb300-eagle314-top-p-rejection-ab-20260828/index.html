1. Reviewer decision

The evidence answers one narrow question: when the target request uses temperature=0.7 and top_p=0.7, does applying the same top-p support restriction to EAGLE’s proposal distribution improve rejection-sampling acceptance?

Supported

Merge the proposal-alignment change behind the existing --speculative-use-rejection-sampling path. The strongest controlled comparison is patched rejection sampling versus stock rejection sampling: +2.7494 pp.

Not claimed

No causal throughput result, no quality comparison, and no claim that stock rejection sampling is mathematically incorrect. The patch changes proposal efficiency, not the target distribution.

Why the comparison is useful. The stock and patched rejection arms used the same request ordinals, source bytes, sampling fields, output controls, deterministic request seeds, EAGLE shape, thresholds, and healthy physical node for both shards.

2. What changes

The target side already applies temperature and top-p. Stock EAGLE rejection sampling temperature-scales the draft logits but leaves the draft proposal untruncated. The patch aligns the draft proposal’s support with the request.

1 · Draft logitsOne vocabulary row from the EAGLE draft model.
→
2 · TemperatureCompute softmax over draft logits divided by request temperature.
→
3 · Request top-pKeep the nucleus support, renormalize, sample from it, and retain that exact distribution.
stock q = softmax(draft_logits / T)
patched q = top_p_renorm(softmax(draft_logits / T), request_top_p)
Scope. This experiment had no request top_k. The proposed change aligns top_p; it does not add draft-side request top-k filtering.

5. Correctness invariant

Rejection sampling remains exact for an arbitrary proposal distribution q, provided the verifier uses the exact same q that generated the proposal token.

sample X ~ q
accept X with probability min(1, p(X) / q(X))
if rejected, sample from normalize(max(p − q, 0))
  1. The patch computes q by applying request temperature and top-p to draft logits.
  2. The draft token is sampled from that returned q.
  3. The same q tensor is retained in draft_probs.
  4. The verifier consumes that retained q for acceptance and residual recovery.
Important distinction. Stock temperature-only q is not distributionally invalid. It is less aligned with the target’s top-p-truncated p, so more proposals can fall outside useful target support and be rejected. This MR optimizes acceptance while preserving the exact-q invariant.

GPU semantic validation

The isolated GB300 patch was checked against an independent reference calculation on three nontrivial rows: exact match reported true; row sums were 1.0, 0.99999994, and 1.0; retained support sizes were 3, 3, and 1. The current MR implementation was also checked on an NVIDIA H20: maximum absolute error 7.45e-9 and maximum row-sum error 1.19e-7.

6. Audit trail and caveats

Pairing

All arms used the same 10,000 request ordinals. Metadata mismatch count was zero, source shard hashes matched, and all request seeds matched by ordinal.

Invalid rows

Exactly 15 rows returned source-level HTTP 400 in every arm. Their ordinals and safe fingerprints matched and they were excluded from speculative denominators.

Privacy

The replay output retained aggregate and per-request metrics, but did not persist prompts, tools, source IDs, generated response text, or raw errors.

Hardware rescue

Node 136 developed repeatable NVIDIA Xid 31 faults after its valid baseline shard. Stock and patched comparison shards were rerun from scratch on healthy node 131.

Core comparison survives the rescue. Stock rejection and patched rejection ran on the same healthy physical node for both shards. The partially cross-node caveat applies to comparisons against the rejection-off control, not to the primary +2.7494 pp stock-versus-patch result.
Version boundary. The 10,000-request A/B used runtime commit ef7977e8… and a narrowly injected two-file patch. The merge request ports the same proposal semantics onto dev at base 83b71ad65…, where proposal helper and multi-layer graph paths have since evolved.

7. Merge-request implementation and tests

The current change applies the proven transformation across the proposal paths present on today’s dev, without touching the non-rejection proposal behavior.

  • Apply temperature then per-request top-p in renorm_draft_probs.
  • Make sample_draft_proposal sample and return the same top-p-renormalized q.
  • Carry top-p through standard EAGLE CUDA-graph static inputs and replay copies.
  • Carry top-p through multi-layer EAGLE’s single-graph in-graph proposal path.
  • Keep rejection sampling off on the original plain-softmax path.
