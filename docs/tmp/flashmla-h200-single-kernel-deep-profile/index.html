Why One FlashMLA Kernel Takes ~106 µs

A fresh, isolated rerun follows one sparse FP8 decode kernel from its 132-CTA launch shape through warp eligibility, memory service, barriers, Tensor activity, and source/SASS work. The aim is not just to name a bottleneck, but to show which evidence supports each part of the explanation.

Fresh ordered-unique reproduction · five one-replay captures 105.632 µs

The historical walkthrough measured 103.424 µs. This fresh reproduction is only 2.208 µs, or 2.135%, longer. Random order measures 110.112 µs; one-hot reuse measures 80.352 µs.

Answer First: the Kernel Is Dependency-Limited, Not One Cleanly Isolated “HBM Phase”

The fresh profiles support one cohesive story. Sparse loads make the producer late; the producer’s ready barrier then makes both consumer warpgroups late. One large CTA occupies each SM, so the scheduler has little unrelated work with which to hide those waits. At the same time, cache-hot data does not erase the substantial address, conversion, shared-memory, softmax, Tensor, and synchronization program that every tile still executes.

Five ordered-unique, one-replay NCU captures span only 105.280–105.664 µs. Their median is within 2.135% of the historical main-kernel mean.

Fresh counters

The deep random report records 29.019% issue-active and 70.981% no-issue cycles, with only 0.353 eligible warps per scheduler cycle.

Interpretation

Waiting propagates across the relay

Long-scoreboard and barrier pressure move together when address reuse changes. This is consistent with WG2 load service delaying the ready barrier consumed by WG0 and WG1.

The essential reading rule: memory service, conversion, shared-memory publication, online softmax, HGMMA, and barriers overlap inside one double-buffered critical path. No profiler counter turns the ~106 µs rectangle into clean, additive stopwatch phases.

One Large CTA Occupies Each of the H200’s 132 SMs

The launch is one wave: 132 CTAs for 132 SMs. Each CTA contains three 128-thread warpgroups. The block uses 168 registers per thread—64,512 registers across 384 threads—and allocates 231,424 B of dynamic plus 1,024 B of driver shared memory: 232,448 B (227 KiB) against the SM’s 233,472 B (228 KiB) configuration. Registers and shared memory each independently prohibit a second CTA, leaving 12 resident warps and 18.75% theoretical warp occupancy.

WG2

132 cells = 132 SMs = 132 CTAsorange: 25-CTA nominal 29-tile scheduler class
Why low occupancy matters here: occupancy is not itself a performance score. It matters because a warp stalled on a sparse dependency cannot be hidden behind a second unrelated CTA on the same SM. The scheduler can only search among the other warps of this same producer/consumer pipeline.

The scheduler metadata contains 25 × 29-tile, 25 × 27-tile, 75 × 24-tile, and 7 empty partitions: 3,200 tiles across 125 work-bearing CTAs. The 29-tile class is the nominal arithmetic maximum, not a directly proven runtime straggler; a 24-tile CTA carrying two request fragments can compete because it executes extra Q prologues and output epilogues.

The Kernel Is an Overlapping A/B Relay, Not a List of Serial Stages

WG2 prepares the next 64-record tile while WG0 and WG1 consume the current tile. Two shared-memory buffers alternate. A producer load delay matters end to end because the buffer-ready barrier is a dependency edge into both consumer warpgroups.

Where fresh PC samples land

Of 10,766 fresh random-unique PC samples, 3,986 are classified as barrier and 3,664 as long scoreboard—71.05% together. The top next-PC locations line up with the source dependency chain rather than one inexplicably slow arithmetic instruction.

WG1 · barrier samples2,965The sample is attributed to the next UMOV PC, but the warp is actually waiting at the preceding barrier. The UMOV itself is not being timed as expensive.
WG0 · long scoreboard1,689Next-PC branch at the K-buffer-ready try-wait path. This localizes the dependency edge by which a late producer blocks QK consumption.
WG2 · long scoreboard788 + 301Next-PC SEL locations consuming sparse-load results. The samples point to pending load data, not intrinsic SEL latency.

PC sampling uses next-PC attribution. Counts identify locations and dependency chains where sampled warps wait; they are not per-instruction microseconds and cannot be divided by the total to obtain an exclusive time share.

PM warp-state lanes are separate replays. Barrier is in PM group 0, long scoreboard in group 2, short scoreboard in group 3, and wait in group 4. Their curves must not be aligned as simultaneous timestamps. Full-window mean sampled activity shows locality nearly halves long-scoreboard activity, while sampled barrier activity remains essentially unchanged and other now-visible waits rise; none may be added or converted to microseconds. This sampled-barrier statement is distinct from the aggregate 15-pass barrier ratio above, which falls from 3.603 to 2.726 warps per issue-active cycle.

Limits, Reproduction Trail, and Downloads

The experiment is unusually controlled, but it is still a synthetic single-GPU reproducer. The strongest conclusions concern this exact kernel specialization and the mechanism exposed by controlled address changes.

Main kernel only

The report deliberately excludes the dependent combine kernel and does not claim to equal a complete layer’s sparse-attention union.

Synthetic addresses

Random, ordered, and one-hot patterns isolate address service. None is claimed to reproduce the online selected-index distribution.

One executing GPU

All eight GPUs were reserved for isolation, but the reproducer profiles one H200 and does not measure TP communication.

Profiler replay

The 15- and 21-pass reports perturb execution and cache state. Their counters diagnose behavior; their durations are not headline timing.

Stalls overlap

Warp-state ratios describe resident warps in states per issue-active cycle. They are not exclusive time percentages and cannot be summed.

Source inventory ≠ cycles

Static and dynamic SASS counts show executed work, but dependencies, pipeline concurrency, and repeated loops prevent direct count-to-time conversion.

No instrumented phase slices

A clock64() rebuild would add instructions to an already register- and shared-memory-limited binary, while the three warpgroups would still overlap. This report preserves the production binary and leaves exclusive source-group times explicitly unknown.
