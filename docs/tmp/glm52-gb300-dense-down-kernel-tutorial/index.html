01

Vocabulary before arithmetic

“Block” means four different things here.

Most early confusion is not about matrix multiplication. It is the same word being reused at four layers of the stack. Keep these objects separate and the rest becomes mechanical.

A · software work unit

CUDA block = CTA

A thread block and a cooperative thread array are two names for the same scheduled unit. This kernel puts 256 threads, or eight 32-thread warps, in each CTA.

B · output ownership

GEMM output tile

One useful CTA owns a rectangular patch of Y: BLOCKM × BLOCKN. Here BLOCKN is 128 while BLOCKM changes with M.

C · reduction progress

K slice

The CTA cannot consume all 1536 reduction values at once. It advances through chunks of BLOCKK = 128, so the accumulation has exactly 12 slices.

D · numerical metadata

FP8 scale block

The “128 × 128 block” in the quantization description says which values share scale metadata. It is not the CTA’s output tile and it does not imply BLOCKM = 128.

Hardware and software hierarchy

A CTA is a task. An SM is a worker.

The GPU scheduler assigns CTA tasks to physical streaming multiprocessors. Threads form warps; warps form a CTA; two CTAs form this kernel’s cluster; all CTAs together form the launch grid.

The sentence to remember

A CTA is a 256-thread software team assigned to one physical SM; for this kernel, that team computes one BLOCKM × 128 output tile at a time.

Freeze the operation

What exactly is the kernel being timed?

This is one TP8 rank’s dense FFN down projection. It is not a routed MoE expert kernel. The profiler row combines online activation quantization with the FP8 DeepGEMM that produces the BF16 output.

256

Threads cooperate

Eight warps belong to the CTA. DeepGEMM specializes warp roles around loading, matrix math, scheduling, and the epilogue; they are not 256 independent copies of the GEMM.

2

CTAs form a cluster

The JIT uses two-CTA clusters. Cluster launch and TMA multicast let a pair coordinate operand movement, so useful CTA counts occur in pairs.

207–225 KiB

Shared memory limits residency

Each CTA requests roughly 211–230 KB of dynamic shared memory. Against 228 KiB per SM, this is a deliberate one-resident-CTA-per-SM design.

12 → 7

Pipeline depth adapts

As BLOCKM grows, each stage costs more storage. The JIT reduces pipeline stages from 12 to 7 to remain within the shared-memory budget.

05

Turn the curve into causes

Runtime follows waves and tile shape—not logical FLOPs alone.

The JIT is actively reshaping the work to keep it inside one scheduling wave. That is the missing variable between “500× more useful FLOPs” and “only 1.50× more elapsed time.”

I

Pay the fixed floor

Launch, persistent scheduling, TMA setup, barrier machinery, pipeline fill/drain, and the fixed weight-tile path exist even when M = 1. Small inputs cannot make those costs disappear.

II

Fill idle workers first

Moving from 48 to 96 to 144 useful CTAs mostly activates SMs that were waiting. Parallel work increases much faster than wall-clock time.

III

Avoid a second wave

The DeepGEMM heuristic explicitly favors a single wave. From M = 100 to 500 it enlarges BLOCKM so the launch remains 144 useful CTAs.

Then why does M = 500 rise to 10.50 µs?

One wave is not the same as constant work per CTA.

The wave count stays one, but each useful CTA owns a much taller output tile: 176 rows instead of 16. It moves more activation data, performs more UMMA work, and has only seven pipeline stages instead of twelve. Online quantization also has more rows to process.

The resulting prediction is qualitative but strong: a long plateau, then a gentle within-wave rise—not a 500× line.

Account before classifying

Why the row term is 15,360M bytes—not 1,536M.

The input width alone is only an element count. A byte model must include dtype size, reads, and writes. The output row is four times wider than the input row.

08

Transfer the reasoning

A nine-question worksheet for any linear kernel.

Use this order. Each answer removes one class of bad explanation before you fit a performance model.

  1. 01

    What is the exact operation?

    Write M, N, K, input/output dtypes, and whether quantization, bias, activation, or communication is fused into the timed range.

    contract
  2. 02

    Which dimension changes?

    Hold the others visibly fixed. A batch sweep changes M; a hidden-width comparison may change K or N, which bends the curve differently.

    independent variable
  3. 03

    What tile did the JIT really choose?

    Recover BLOCKM, BLOCKN, BLOCKK, thread count, cluster shape, and pipeline stages. Never assume them from the FP8 scale-block shape.

    launch geometry
  4. 04

    How many useful output tiles exist?

    Count ceiling divisions along M and N. Their product is the useful CTA-task count for a conventional one-tile-per-task view.

    parallel tasks
  5. 05

    How many tasks can run at once?

    Start with SM count, then reduce it if registers, shared memory, CTA clusters, or kernel occupancy permit fewer resident tasks.

    wave capacity
  6. 06

    Where are the wave knees?

    Divide useful tasks by wave capacity and round up. A transition from one to two waves is a strong candidate for a runtime step.

    scheduling shape
  7. 07

    How full are the boundary tiles?

    Compare logical rows and columns with tiled extents. Tiny M can execute a minimum tile even when only one row is useful.

    padding
  8. 08

    What is fixed, and what grows?

    Separate weights, startup, and pipeline fill from activation reads, output writes, and arithmetic. This predicts floor versus slope.

    cost model
  9. 09

    What did the cache and clock actually do?

    Use a warm-up policy, report cache state and clocks, then measure at least one point per tile region and around every predicted wave boundary.

    calibration

A visual grammar of kernel curves

Read shape as a short list of hypotheses.

Fixed floor

Launch, setup, and minimum-tile work dominate.

Parallel-fill plateau

More tasks occupy previously idle SMs.

Wave knee

Useful tasks cross resident capacity.

JIT sawtooth

Tile or layout changes reset padding and pipeline choices.

Asymptotic slope

Compute or bandwidth finally scales with useful work.

Two thought experiments

Change one dimension and predict before profiling.

Double N

6144 → 12,288

Keeping BLOCKN = 128 would double N-tile columns from 48 to 96. At M = 100 and three row tiles, 288 CTA tasks require two waves.

First hypothesis: a scheduling step—unless the JIT changes tile width or occupancy.
Double K

1536 → 3072

Output tile count does not change, but each CTA advances through 24 rather than 12 reduction slices and the weight matrix doubles.

First hypothesis: a higher per-wave slope, without a tile-count knee.
09

Close the loop

If these answers feel obvious, you are ready for the next kernel.

Open each checkpoint only after answering it yourself. The goal is not memorizing 152 or 128; it is learning which quantity to ask for.

1If useful CTA count doubles but remains within one wave, must runtime double?

No. The added CTAs can occupy previously idle SMs. Runtime rises mainly if work per CTA grows, occupancy changes, or tasks spill into another wave.

2Does a 128 × 128 FP8 scale block prove that the GEMM uses BLOCKM = 128?

No. Scale grouping is a numerical-format choice. GEMM tile geometry is a JIT scheduling choice. The measured kernels use BLOCKM values from 16 through 176.

3Why do M = 100, 200, and 500 all launch 144 useful CTA tasks?

The JIT raises BLOCKM from 48 to 80 to 176. Each case therefore needs exactly three M-tile rows, and three times 48 N-tile columns equals 144.

4Why can M = 500 still be slower when it remains one wave?

Each CTA’s tile is taller, activation traffic and arithmetic increase, online quantization processes more rows, and pipeline stages shrink. “One wave” constrains scheduling multiplicity; it does not make every CTA equally cheap.

5What is the first calculation for an unfamiliar GEMM?

After recovering the actual JIT tile, compute ceiling-divided M tiles times ceiling-divided N tiles. Then compare that task count with resident CTA capacity.
