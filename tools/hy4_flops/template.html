C is used by the indexer on each of its 21 refresh layers. S is used by sparse MLA on every one of the 78 layers. A shared-index layer reuses selection IDs; it still computes its own queries, KV, attention outputs and FFN.

Arithmetic convention: GEMM = 2mnk; fused multiply-add = 2 FLOPs. Scalar exp, reciprocal, division and reciprocal square root each count as one logical operation; sign changes, comparisons, casts, indexing, memory movement and communication are excluded. This is an expanded mathematical ledger, not a hardware instruction counter. Softmax/RMSNorm use the same operation-count convention as the GLM page.

The dimensions below are whole-model shapes before TP partitioning. A chunked implementation can process the 100K prompt in smaller pieces while retaining these useful arithmetic totals; it need not materialize a full 100K-by-100K matrix. Chunk boundaries, padding and scheduling can change executed work and wall time.

The new expensive gate is a different gate

G=σ(UWgate),   Wgate ∈ ℝ6,144 × 16,384

This elementwise MLA output gate has 100,663,296 weights per layer and costs 20.132659 TFLOP per layer at 100K tokens. Across 78 layers its projection alone adds 1.570347 PFLOP. It is applied after 512-to-256 value expansion and before the 16,384-to-6,144 output projection. The iHC projections, by contrast, have only eight outputs per sublayer.

Attention: same main backbone, one large extra GEMM

The query-A/KV-A, query-B, absorbed query, value expansion and output projection dimensions match. So do sparse QK/PV dimensions and the total number of selected pairs. HY4 adds the output gate. Its sink adds only one extra denominator term per query/head, not an extra attended value. The gate is a substantial FLOP change; the sink is not.

Both have 21 refresh layers, so their total DSA scoring/setup work matches. But layer 2 drops its selector in HY4, while layer 5 gains one. A full refresh costs about 43.158851 TFLOP beyond a shared-index layer at this prompt length. This can outweigh the gate difference in an individual aligned layer. Exact reconciliation with the published GLM total

The original page sums to 10,945,320,321,466,784 FLOPs. Its MoE combine convention charges 17H per token: nine weight multiplications and eight additions, including multiplication by the shared expert's unit weight.

Here both models use the source-aligned expression: eight routed weight multiplications, seven routed additions and one unweighted shared addition, or 16H. Therefore subtract 100,000 × 75 × 6,144 = 46,080,000,000 FLOPs from the original GLM ledger, giving 10,945,274,241,466,784 FLOPs. The correction is about 0.00042%; it is disclosed rather than hidden in rounding.

All other GLM leaf costs exactly reproduce the original expanded ledger. Routed scaling is represented in the eight route weights for both models; a backend applying it to the final vector executes a slightly different scalar operation count.

06   Why +@@PERCENT@@% FLOPs is not a latency estimate

Source-derived behaviorRuntime consequence / limit of this ledger
Sink-enabled sparse backendOur pinned DSA backend requires the FlashMLA sparse path when a sink is present. Its sparse wrapper pads local heads to 64 on SM9 and 128 on SM10. For example, an unsharded 64-head Blackwell call is presented as 128 heads, and an attention-TP8 shard with 8 useful heads is also padded to 128. The numerator above counts only 64 useful global heads. Padding can add physical work; exact executed instructions and masked-lane behavior require the chosen kernel/trace.
Sink and combined BMM/attention pathThe MLA eligibility helper rejects the combined query-absorption BMM followed by attention custom-op path when a learnable sink is present. This is not the final value-expansion BMM, nor a claim that both operations become one device kernel. Its source calls the BMM and attention in sequence. A sink changes path eligibility even though its arithmetic contribution is tiny.
Gate kernel choiceOur HY4 code has HPC fused gated-MLA GEMM, Triton and eager fallback paths. Fused gate application can change memory traffic and launches but does not remove the separate learned matrix multiplication.
iHC activation trafficA logical BF16 100K × 4 × 6,144 carrier contains 4.9152 GB, versus 1.2288 GB for one hidden tensor. This is a shape/byte comparison, not measured peak allocation: chunked prefill holds smaller active chunks, and GLM may keep separate hidden/residual buffers. iHC does not quadruple the MLA KV cache.
TP / DP attention / PPThe audited branch supports PP and DP attention. It carries the flattened 24,576-wide iHC state between PP stages, plus top-k IDs at shared-index boundaries. FFN DP synchronization operates on the reduced 6,144-wide input. Replicated small projections, collectives and local padding are not charged to this full-model useful-work ledger. Do not multiply its total by TP size.
MoE routing and shared branchExactly eight routed experts plus one shared expert are counted per token. Token imbalance, grouped-GEMM tile padding, dispatch, quantization and all-to-all affect time. HY4 disables shared-expert fusion because only routed experts use its activation clamp.
Precision and throughputTencent's config declares BF16 weights; iHC projections are explicitly FP32 in our source. Runtime quantization flags and kernel choice can alter compute precision. No precision-equivalent PFLOPs or MFU is claimed. A measured MFU would need precision-compatible peak throughput, actual hardware and a measured interval.

Bottom line: use the tree to identify arithmetic changes and formulate kernel experiments. Use an actual HY4 profile to answer how much slower or faster it runs. A small scalar feature can change an entire kernel path; a large FLOP increase can partly overlap other work.
